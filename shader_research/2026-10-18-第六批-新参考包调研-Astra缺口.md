## 三、7 条候选（按性价比排序）

### 1. 远景光源散景 —— 本轮最佳，成本 4 次取色 ⭐

**这条解决什么问题。** 现在你在远处看到一支火把或一个灯笼，它只是暗淡的一小块。真实相机里，远处的发光点会因为衍射和散射膨胀成一个柔和的光斑。散景就是补这个。

**怎么做的（极简）。** 只对距离超过 60 格的像素生效，混合比例随距离线性上升：

```glsl
// _analysis/refs-2026-10-18/allium-shaders/shaders/lib/misc/distantLightBokeh.glsl:1-3
float GetDistantLightBokehMix(float lViewPos) {
    return clamp01(0.005 * (lViewPos - 60.0));
}
```

然后在延迟合成阶段，取自身 + **上下左右 4 个邻居**的颜色相加后乘 0.2，再用 max 保底，按上面的比例混合：

```glsl
// allium-shaders/shaders/program/deferred7.glsl:289-299
int dlbo = 1;
vec3 dlbColor = color;
dlbColor += texelFetch(colortex0, texelCoord + ivec2( 0, dlbo), 0).rgb;
dlbColor += texelFetch(colortex0, texelCoord + ivec2( 0,-dlbo), 0).rgb;
dlbColor += texelFetch(colortex0, texelCoord + ivec2( dlbo, 0), 0).rgb;
dlbColor += texelFetch(colortex0, texelCoord + ivec2(-dlbo, 0), 0).rgb;
dlbColor = max(color, dlbColor * 0.2);
color = mix(color, dlbColor, GetDistantLightBokehMix(lViewPos));
```

关键是 `max(color, ...)` —— 只做"向外膨胀变亮"，**不会把画面整体糊掉**。所以暗处不受影响，只有本来就亮的发光块会散开。

还有一条更省的细节：按 **纹理 mip 等级**衰减。远处方块本身已被压缩成几个纹素，此时才需要散景：

```glsl
// distantLightBokeh.glsl:8-9
float GetDistantLightBokehMixMipmapped(float lViewPos) {
    return GetDistantLightBokehMix(lViewPos) * min1(miplevel * 0.4);
}
```

此外还可以按材质指定自己的"远景色"，例如给火把指定橙色：`DoDistantLightBokehMaterial(color, vec4(1.0, 0.6, 0.2, 1.0), emission, 5.0, lViewPos)`（`terrainMaterials.glsl:1369`）。

**Astra 的证据〔实测〕。** `distantLightBokeh|miplevel|distantColor` 全树 **0 命中**。Astra 的远处发光方块就是原始 albedo，没有任何膨胀处理。

**怎么落地。** 不需要新附件、不需要新 pass。直接在 Astra 的延迟/deferred 合成里，对 `lViewPos > 60` 且 `emission > 0` 的像素插这段。**推荐先只交 textures+max 版本**（约 4 次 texelFetch + 1 次 max），发布前再考虑 per-material pack。

**成本。** 4 次取色，只在远处执行（其余像素 `dlbMix` 为 0）。估计每像素增加约 4 次 texelFetch。**未验证**——没有实机帧时。

**落地依赖（复核时新查，重要）。** 上面那段参考实现用了 `miplevel` 这个变量。Astra 全树搜 `miplevel|textureQueryLod` **为 0 命中**——**Astra 没有这个现成变量**，那个按 mip 等级衰减的省算写法不能原样搬。落地时要么自己用屏幕导数（`textureQueryLod`/`dFdx` 一类）算出一个等价量，要么干脆去掉这一层衰减、只用距离判据。这一层属于可选优化，去掉也不影响主效果。

**风险。** 雨天/雾中的远景糊 —— 因为它是"变亮"，可能在浓雾里产生奇怪的光晕。**建议加一个阈值：只在 `emission` 高于某个值时才散景**，普通地形不受影响。

**许可。** Allium 是 **Complementary CLA 1.5**（不是 MIT）。该许可 1.3 节允许"修改后再分发"，但要求：（a）显著署名并链接官网；（b）保留许可文件**且不得修改**；（c）包名不得含 "Complementary"；（d）**必须在包括白天主世界在内的多个常见场景里与原始包有明显外观差异**。〔读源码：`License.txt:51-69`〕

> **这意味着：不能直接搬代码，但可以自己重写这个思路。** 上面那段核心逻辑只有 10 行，重写没有任何技术难度，注册 Astra 自己的实现即可。**按思路重写不受 CLA 限制**——这也是为什么它排第 1。

### 2. DoF 景深 / 散景虚化 —— Astra 完全没有

**这条解决什么问题。** 现在画面里远近都同样清晰。真实镜头对焦在某个距离上，前景（比如手里的方块）和远景会虚化。Astra **没有任何 DoF**（实测 0 命中）。

**两种现成实现可选：**

**便宜版（BVS）。** 用 60 个固定偏移取一圈，配合 **mipmap 逐级降采样**，并且**跳过手部**（手部不该虚化）：

```glsl
// _analysis/refs-2026-10-18/bvs/shaders/world0/composite2.fsh:82-99
float hand = float(z < 0.56);
float fovScale = gbufferProjection[1][1] / 1.37;
float coc = max(abs(z - centerDepthSmooth) * DOF_STRENGTH - 0.01, 0.0);
coc = coc / sqrt(coc * coc + 0.1);           // 软压缩，防止炸掉

if (coc > 0.0 && hand < 0.5) {
    for (int i = 0; i < 60; i++) {
        vec2 offset = dofOffsets[i] * coc * 0.015 * fovScale * vec2(1.0/aspectRatio, 1.0);
        float lod = log2(viewHeight * aspectRatio * coc * fovScale / 320.0);
        dof += texture2DLod(colortex0, TexCoords + offset, lod).rgb;
    }
    dof /= 60.0;
}
```

注意 `float hand = float(z < 0.56)` —— **深度小于 0.56 就跳过虚化**，这是 BVS 用来排除手部经验的阈值。

> **这里我要修正一处自己写错的话。** 上一版我说"Astra 自己的 deferred 里也在用 `z0 < 0.56` 判断 entityOrHand"，复核时发现**这是我拿参考包的特征套到 Astra 头上了**：全树搜 `entityOrHand` 与 `z0 < 0.56` 均 **0 命中**，搜到的 4 处 `0.56` 全是无关的常数值（`end_geometry.glsl:206`、`end_surface.glsl:7`、`water_palette.glsl:10`、`sky.fsh:74`）。Astra 若要做 DoF，**手部判定需要自己按现有深度语义确定阈值，不能直接沿用 0.56**。

另外它需要 `colortex0MipmapEnabled = true`（`composite2.fsh:108`，已核对）。

**落地依赖（复核时新查，重要）。** 上面 BVS 那段代码直接用了三个量：`centerDepthSmooth`、`gbufferProjection[1][1]`、`aspectRatio`。Astra 全树核对结果：`centerDepthSmooth` **0 命中**、`aspectRatio` **0 命中**。也就是说**这段代码一行都不能直接用**，需要先解决输入：

- **`centerDepthSmooth`**：这是 Iris 提供的"屏幕中心深度"。Astra 没有用是因为它的 DoF 缺失、尚未建立这套对焦模型——**这不是某个功能缺了，而是整个对焦输入要重新设计**。落地时要自己定义"对焦距离"（例如固定值、或由玩家视线命中的深度决定）。
- **`aspectRatio`**：Astra 没用这个 uniform 名，需要用 `viewWidth/viewHeight` 自己算。
- **`texture2DLod`**：Astra 现有代码用的是 `textureLod`（见 `clouds_planar.glsl:96` 等），写法要统一。

**所以第 2 条的"低成本"要打折：它的实际工作量主要在补这三个输入，而不是 60 次取样本身。**

**好看版（Epoch，MPL-2.0）。** 提供 **洋葱圈（onion-ring）边缘增强**和**变形（anamorphic）横向拉伸**：

```glsl
// _analysis/refs-2026-10-18/epoch/shaders/lib/blurs.glsl:11-22  (洋葱圈)
vec3 onionRingBokeh(float blurAmount, sampler2D colortex) {   // 原注释：adds the harsher edges to the bokeh
    for (int i = 0; i < DOF_BOKEH_SAMPLES; i++) {
        float angle = (360.0 / DOF_BOKEH_SAMPLES) * i;
        float polarDistance = blurAmount;
        float hOffset = polarDistance * sin(angle) * hPixelOffset * (1.0/DOF_ANAMORPHIC);
        float vOffset = polarDistance * cos(angle) * vPixelOffset * DOF_ANAMORPHIC;
        retColor += texture2D(colortex, vec2(hOffset + texcoord.x, vOffset + texcoord.y)).rgb;
    }
}   // 完整原文见 epoch/shaders/lib/blurs.glsl:11-22
// :18-19  变形拉长 (变形镜头横向拉伸)
float hOffset = polarDistance * sin(angle) * hPixelOffset * (1.0/DOF_ANAMORPHIC);
float vOffset = polarDistance * cos(angle) * vPixelOffset * DOF_ANAMORPHIC;
```

Epoch 还有 **色差**（`composite15.fsh:39-43`）：uvGreen *= 1.0 + 强度，uvBlue *= 强度*2+1 —— 三个通道用不同缩放，边缘产生彩色镶边。

**许可 —— 这条我必须如实说明证据强弱。**

- **Epoch 的 MPL-2.0 可以确认**：包内有 `LICENSE` 文件，首行就是 `Mozilla Public License Version 2.0`〔读源码：`epoch/LICENSE:1`〕。MPL-2.0 是文件级 copyleft，允许代码级借用，需保留许可并署名。
- **BVS 的 CC-BY-4.0 属于"只有Metadata、包内无佐证"**：我把 ``BVS/`` 目录 71 个文件全列了一遍，**里面没有任何 LICENSE / COPYING / 许可声明文件**，唯一非着色器文件是 ``PATREON.txt``，内容只有一行 `patreon.com/lolip_p`（作者是 lolip_p）。CC-BY-4.0 这个结论**仅来自 Modrinth 项目页的元数据字段，我无法在包内核对**。

**所以要按最保守的执行**：BVS 那段 DoF 代码**先当作"仅思路参考"**，不要直接粘贴；真要落地请用 Epoch 的 MPL 版本（`lib/bokeh/bokeh.glsl` + `lib/blurs.glsl`），或者自己按这个思路重写。若你确实想用 BVS 的代码，需要先去它的 Modrinth 页面确认许可原文。**这是我复核时发现的、原报告写得不够严谨的一处。**

**成本与风险。** 60 次取样很贵。建议：**半分辨率 + 只在 coc 超阈值时执行**（已有这个早退机制）。DoF 会轻微降低锐利度，可能与 Astra 的 TAA/FXAA 叠加后过度柔化。**必须 A/B 截图**。

### 3. RenderPearl 的光源列表 + 手持光光线追踪（MIT，可直接改代码）⭐

这是本轮**结构差异最大**的发现。RenderPearl 完全不用"shadowmap 查遮挡"来做局部光，而是维护一张**场景中的光源列表**。

**为什么值得参考。** RenderPearl 完全不用"阴影贴图查遮挡"来做局部光，而是维护一张**场景中的光源列表**——采集附近真实光源，逐光源按平方反比算贡献。理论上它比屏幕空间折衷（前几轮报告提过的 Velocity 方案）更彻底：不依赖屏幕信息，光源绕到墙后也判得出来。

> **必须如实交代：这条的前提我没有证实。** 我上一版写"Astra 现在的方块光不判断中间有没有墙"，把它当成待修的缺陷。**实际上 Astra 是否真存在"隔墙火把还照亮"这个问题，本会话没有任何证据**——上一轮报告（`docs/参考与取舍.md`）的核验已经明确写过：Astra 放置光源读取的是游戏传入的 `lightcoord.x`（经 `local_light_components` 的 pow4 处理），**不能据此宣布存在隔墙缺陷**。我搜 `through.?wall|occlu|blocklight.*shadow` 也没找到 Astra 自认这个缺陷的注释或 FIXME。
>
**代码事实（已核实，可作为依据）**：Astra 的方块光强度确实只由 `local_light_components()` 算出——核心是 `pow4(blockLight) * (BLOCKLIGHT_STRENGTH * 0.01)`（`Astra/shaders/global/lighting/blocklight.glsl:85-93`，我再核对了 `pow4` 就是这里的），外加白天的 `BLOCKLIGHT_SUPPRESSION` 抑制（`:99-107`）。**整个函数没有任何墙体遮挡项**，只有亮度、强度和日光抑制。所以"不含遮挡判断"是**确凿的代码事实**。
>
> **但"因此有 bug"不成立**：上一轮核验已说明不能据此宣布存在隔墙缺陷，我搜 `through.?wall|occlu|blocklight.*shadow` 也没找到 Astra 自认该缺陷的注释/FIXME。
>
> **所以这条的正确定位是**：它是一个**架构层面的可选方向**（真光源列表 vs 屏幕空间近似 vs 体素传播），**不是"修复某个已确认 bug"**。是否值得投入，取决于你是否真的观察到了隔墙漏光——这个要看实机画面，不是看代码能定的。**我不知道你有没有观察到。**

**关键实现〔读源码〕。**

```glsl
// renderpearl/shaders/lib/light/sample_ll_block.glsl:13-20
immut float16_t light_level = offset_intensity - mhtn_dist;          // :17
float16_t brightness = intensity * falloff;                          // :18
immut float16_t falloff = float16_t(1.0) / (                         // :13-15
    max(sq_dist_light, is_wide ? float16_t(1.0) : float16_t(0.25))
);
brightness *= smoothstep(0.0, LL_FALLOFF_MARGIN, light_level);       // :19
brightness /= min(light_level, 15.0) * (1.0/15.0);  // 抵消后面乘 light.x，让衰减接近平方反比   // :20
// 注：原文是 float16_t(...) 显式构造；为便于阅读做了简化书写，语义一致。
```

这段注释写得很清楚：`offset_intensity == intensity + 0.5` 是为了补偿"光源方块边缘到衰减真正起点"的半个方块 `normalize`。这种对原版光照语义的精细处理值得学。

还有一层**距离淡出到兜底色**，避免光源列表边缘出现硬切：

```glsl
// sample_ll_block.glsl:35-42
// 完整签名（原文 :35）
f16vec3 mix_ll_block_light(f16vec3 fallback_block_light, float16_t chebyshev_dist,
                           float16_t block_light_level, f16vec3 reflected) {
    const vec3 packing_scale = vec3(15u * uvec3(31u, 63u, 31u));                 // :37
    immut f16vec3 ll_block_light = f16vec3(1.0/packing_scale)*block_light_level*reflected; // :38
    return mix(ll_block_light, fallback_block_light,                             // :41
               smoothstep(LL_DIST - 15, LL_DIST, chebyshev_dist));
}
```

**成本与风险。** 这条是**大工程**：光源采集、传播、三步fallback、容量调度都要重做。而且 RenderPearl 用了自己的转译层（`immut`/`f16vec3` 是自定义宏，见 `prelude/compat.glsl:19-23`），**不能直接粘贴**，必须翻译成 Astra 自己的写法。**另外要注意**：RenderPearl 依赖 `#version 460` + 厂商扩展（NV_gpu_shader5 / AMD_gpu_shader_half_float，`compat.glsl:26-40`），Astra 的兼容性约束更宽，**不能连它的 compat 层一起搬**。

**建议定位：中长期方向。** 这条路能从根本上解决"隔墙火把还照亮"（不用屏幕空间折衷的真遮挡），但需要全新工程量，绝不是一两天的事。

### 4. DH（Distant Horizons）远景地形 support —— Astra 的 Voxy 还是空的

**发现：** 本轮下载的 9 个包里，**5 个都有 `dh_*` 入口**——`allium`（三维度都有 dh_terrain/dh_water）、`bvs`（三维度都有）、`vanilletix`、`renderpearl`、`glimmer`。这足以说明 DH 支持是当前主流光影包的标配。Alpha Piscium 也在 `shadowcomp1.csh:55-60` 同时处理 `DISTANT_HORIZONS` 和 `VOXY`：

```glsl
#if defined(DISTANT_HORIZONS)
    uniform float dhNearPlane;
    uniform float dhFarPlane;
#elif defined(VOXY)
    uniform int vxRenderDistance;
#endif
```

**Astra 的现状〔读源码〕。** Voxy 开关明确标注未实现：
- `lang/zh_CN.lang:177`：`option.voxy_support.comment=预留的适配开关。voxy 远景渲染尚未实现，启用此选项不会产生渲染效果。`
- `lang/en_US.lang:177`：`voxy distant-terrain rendering is not implemented`
- 云雾/雾里有两处注释提到 voxy draws，但那是同一文件的注释，不是渲染路径。

**为什么推荐 DH 而不是 Voxy。** DH（Distant Horizons）是**当前装机量最大的远景方案**，生态成熟度比 Voxy 高得多。

**怎么做。** `gbuffers_dh_terrain` / `gbuffers_dh_water` 两个入口 + `dhNearPlane`/`dhFarPlane` 两个 uniform，让远景地形走 Astra 已有的 lit/deferred 链。**难点**：DH 远景有自己的深度范围，不能直接用 vanilla 的 near/far 反推线性深度，需要一个单独的深度还原分支。

**许可。** DH 入口本身只是 Iris 程序名，**不涉及第三方代码**，可直接实现。

**成本。** 中等（2 个新入口 + 深度处理 + 雾适配）。

**前提已核实（本轮补）：本机没有装 DH。** 我按 `qa/local_paths.json` 指向的实例检查了 mod 目录：

```

 iris-fabric-1.11.2+mc26.2.jar   1 个（在）
```

〔实测，读 mod 目录〕**这条曾经标着"未验证"，现在已经明确了：实例里没有 Distant Horizons。** 所以第 4 条在当前机器上做出来就是“写了一组永远不会被调用的入口”，纯属无用功。**除非你打算装 DH，否则这条应直接搁置**，不要排在前面。

### 5. Glimmer：蓝噪声 + Vogel 圆盘 + TAA 相关的整套低差异基础设施（MIT）

Glimmer 是 MIT，这三条都能直接改。

**(a) 蓝噪声。** 蓝噪声的好处是"频谱集中在高频、没有低频结构"，比白噪声或纯 Halton 更快收敛、也不容易产生条带。Astra 全树搜 `blueNoise` **为 0 命中**，确实没有。

> **复合核时发现我上一版把这里写错了。** 我原来写"替换现有抖动（Halton 在 `lib/taa_jitter.glsl` 等）"，暗示 Astra 有一套可被替换的噪声纹理设施。**不是这样**：`Astra/shaders/lib/settings.glsl:460` 明确写着 `// noisetex/noise.png were removed: nothing sampled them (consolidated review e4).`，也就是 **Astra 已经专门删掉了没人采样的噪声纹理**，并用 `AStra_cloud_ign()`（交织梯度噪声，见 `clouds_planar.glsl:209`）这类**函数式程序化噪声**替代查表。
>
> **所以这不是"升级抖动"，而是"要不要为了某个具体效果新引入纹理查表"**——而 Astra 已经用整合审查的结论否掉了查表路线。落地前必须先回答：哪个具体效果真的需要蓝噪声而程序化噪声不够？否则这条应当**降级为"暂不需要"**。这是我复核时发现的方向性错误。

```glsl
// glimmer-shaders/shaders/lib/common/util.glsl:133-139
#define BLUE_NOISE_RESOLUTION 1024
vec4 blueNoise(vec2 texcoord) {
  ivec2 sampleCoord = ivec2(texcoord * vec2(viewWidth, viewHeight));   // ← 关键：先换成像素坐标
  sampleCoord = sampleCoord % ivec2(BLUE_NOISE_RESOLUTION);
  return texelFetch(blueNoiseTex, sampleCoord, 0);
}
// :142-150 时域版本 —— 每帧换 shift，避免静止画面用同一噪声
vec4 blueNoise(vec2 texcoord, int frame) { ... }
```
```
// glimmer-shaders/shaders/shaders.properties:27  配合 customTexture
customTexture.blueNoiseTex = /textures/blueNoise.png
```

Astra **已有 customTexture 机制**（`shaders.properties` 里 12 处先例），所以落地只是"加一张图 + 一个 include"。

**(b) Vogel 圆盘**用于 阴影/IPBR 摆动采样，比随机点均匀：
```glsl
// glimmer-shaders/shaders/lib/lighting/shadows.glsl:148
vec3(vogelDiscSample(i, SHADOW_SAMPLES, noise), 0.0) * sampleRadius;
```

**注**：上一轮报告已经确认 Astra **已有等价物**（`program/ssao.fsh:35-49` 的 12 点黄金角常量表）。所以** Vogel 本身不算缺口**，列在这里是因为它和蓝噪声是同一套下游设施。

**(c) 自动曝光拆分到独立 compute pass**（`program/c49_computeAutoExposure.glsl` + `c50_applyAutoExposure.glsl`）。Astra 已有 8×8 对数域 64-tap 测光 + 1×1 历史，所以**这条是同一档位的另一种组织方式**，价值最低，可以先不做。

**许可。** Glimmer **MIT**，可直接改代码。

### 6. Vanilletix：SSGI / 镜头炫光 / 运动模糊 / LabPBR 视差

vanilletix 是 FlameRender 许可（**限制较多，建议只学思路**），但它有四项 Astra 确实没有的完整实现：

**(a) 真 SSGI** —— 屏幕空间 GI，一次弹射，非常简单：
```glsl
// vanilletix/shaders/lib/lighting/complexShadingDeferred.glsl:9-13
vec3 SSGIcoord = rayTraceScene(screenPos, viewPos, generateCosineVector(normal, noiseUnitVector), dither.z);
if (SSGIcoord.z > 0.5) sceneCol += albedo * textureLod(colortex5, getPrevScreenCoord(SSGIcoord.xy), 0).rgb;
```
作者自己在 `settings.glsl:69` 注释：`Currently experimental and noisy`。配套有 `PREVIOUS_FRAME` 支持无限次弹射（`:76`）。

**(b) 镜头炫光**（Astra 只有 cloudous.horizon glow，无 lens flare）：
```glsl
// vanilletix/shaders/lib/post/lensFlare.glsl:38-65
float lensFlareRays(in vec2 centerCoord, in vec2 lightDir, in float rayBeam, in float size, in float dist) {  // :42-47
  vec2 flareCoord = centerCoord + lightDir * dist;
  float rays = max(0.0, sin(atan(flareCoord.x * aspectRatio, flareCoord.y) * rayBeam));  // 放射状光条
  float lens = lensFlareSimple(centerCoord, lightDir, size, dist);
  return rays * lens + lens;
}

// :56-62 —— 三档不同距离产生色散（红绿蓝分离），这就是彩虹边
vec3 chromaLens(in vec2 centerCoord, in vec2 lightDir, in float chromaDist, in float size, in float dist) {
  return vec3(
    lensFlareSimple(centerCoord, lightDir, size, dist),
    lensFlareSimple(centerCoord, lightDir, size, dist * (1.0 - chromaDist)),
    lensFlareSimple(centerCoord, lightDir, size, dist * (1.0 - chromaDist * 2.0))
  );
}
```

**(c) 运动模糊**（`lib/post/motionBlur.glsl`，需 velocity buffer）。

**(d) LabPBR 视差遮蔽**（`lib/PBR/labPBR.glsl:100-213` + `PARALLAX_SHADOW`）—— 需要资源包支持 LabPBR 才有意义。**Astra 目前没有任何 PBR 材质路径（实测 labPBR/labPBR 0 命中），这条优先级最低。**

**Astra 证据〔实测〕。** `SSGI|lensFlare|motionBlur|parallaxOcclusion` 全部 **0 命中**。

**怎么取舍。** SSGI 上一轮报告已讨论过（当时卡在 colortex15 只在 TAA 档分配、TAA 关闭时无历史可用的依赖冲突）。**这两条 SSGI 与运动模糊列在这里作为"可行依据补充"**，真正值得优先的是 **(b) 镜头炫光**——它便宜、明显、且和 Astra 已有的 FXAA/TAA/Bloom 链不冲突。

### 补录：Musk Rose（CC0-1.0）——本轮下载了却漏分析的一个包

上一版我列了 9 个包，正文却只分析了 8 个，**Musk Rose 4.1 被我下载解压（223 个文件）、却在正文里 0 次提及**。这里补上核实结果，避免它被当成“没查过”。

**结论：它没有带来新候选，但有两条值得知道的事实。**

- **它的 SSAO 是“SSDO 派生的普通屏幕空间 AO”，不是能弹射颜色的间接光。** 出处写在文件里：`musk_rose_ssao.glsl:34-37` 注明 `Generate SSAO based on SSDO by Yuriy O'Donnell. See: https://github.com/kayru/dssdo`。我把整个实现读完了（全文 65 行，`getSSAO` 就是累积遮挡项然后返回），**里面没有任何颜色/辐射度弹射**，只有 `sqrt(max(dp,0.0)) * attenuation² * step(0.1, dp)` 这类可见性加权。调用方是把它和原版 AO 直接相加（`world0/deferred.glsl:59`：`vanillaAO * AO_VANILLA_INTENSITY + getSSAO(...) * AO_SHADER_INTENSITY`）。
- **所以它对 Astra 不构成新机制**：Astra 已有**半分辨率带 bent normal 的 SSAO**（`lib/ao_resolve.glsl`、`diffuse.glsl:425,493` 提到 bent normal 与 SH 辐照度替换），比这个更完整。**不要因为我提到 SSDO 就以为这里有 GI。**
- **它真正有意思的两点在别处**：一是 `#define LAB_PBR 2` 且支持 `PBR_TEXTURE = AUTO_GENERATION`（`musk_rose_config.glsl:11,90`），即**不依赖 LabPBR 资源包也能从原版纹理自动推导 PBR 属性**——Astra 目前完全没有任何 PBR 材质路径（实测 0 命中），若将来想做，这是 CC0 的现成参考；二是**水体视差**（`ENABLE_WATER_PARALLAX`，`musk_rose_config.glsl:70-71`，6 步）。但 `docs/当前工作.md` 已记录“单像素折射与取消视差：已落实”，所以这条**不能直接算缺口**。

**许可**：Musk Rose **CC0-1.0**（元数据 + 包内 LICENSE），是本次所有包里限制最少的，**理论上可直接复制代码**。但它引用的 dssdo 是上游项目，Astra 若要借那段需另看 kayru/dssdo 的许可（社区普遍称 MIT，**但我本轮没有直接读它的 LICENSE，未核实**）。
