## 一、新候选（按性价比排序）

### 候选 1：地面雨滴溅落闪光（推荐首选）

**这是什么**：下雨的时候，朝上的湿表面（石头顶面、路面、屋顶）会随机闪现一些小亮斑，像雨点刚砸在地上溅起来的那一瞬间反了一下光。它是**加亮**，不是画粒子。

**参考实现（已读源码，13 行）**：velocity-shaders `shaders/program/deferred1.fsh:119-131`：

```glsl
#ifdef HELIOS_RAIN_SPLASH
if (Depth < 1.0 && distSq < 900.0) {
    vec3 packedNormal = texture(normals, texcoord).xyz;
    float upDot = clamp(packedNormal.g * 2.0 - 1.0, 0.0, 1.0);
    if (upDot > 0.6) {
        float splashNoise = texture(noisetex, gl_FragCoord.xy * 0.3 + frameTimeCounter * 0.5).r;
        float splash = splashNoise * splashNoise;
        splash = splash * splash;
        splash = splash * splash * rainStrength * HELIOS_RAIN_SPLASH_INTENSITY;
        Color.rgb += vec3(0.7, 0.75, 0.85) * splash * upDot;
    }
}
#endif
```

四个设计点值得学：

- `Depth < 1.0` 排除天空像素（深度 1.0 是远平面），`distSq < 900.0` 限制在 30 格内——远处的溅落看不清，不值得算。
- `upDot = clamp(packedNormal.g * 2.0 - 1.0, 0.0, 1.0)`：法线贴图里 G 通道是编码过的（0 到 1），乘 2 减 1 还原成 -1 到 1 的真实分量，这里取的是"朝上程度"。`upDot > 0.6` 就是只让比较水平的面参与。
- **噪声连乘三次平方等于八次方**（`splash = n*n` 三次 → n⁸）：这是关键技巧。八次方把噪声压成极稀疏的尖峰——大部分像素接近 0，只有少数几个点冲到高值，于是看起来是"一个个独立的亮点"而不是"一片均匀的噪点"。
- 噪声坐标是 `gl_FragCoord.xy * 0.3 + frameTimeCounter * 0.5`，即**屏幕空间**加时间滚动。屏幕空间意味着相机转动时亮点会跟着屏幕跑而不是跟着世界跑，这在雨溅这种短寿命、高随机的效果上是可以接受的（玩家不会注意到单个亮斑的世界位置漂移），而且比世界空间量化便宜。

**Astra 缺口证据（实测 + 读源码）——这条需要特别说明**：

grep `rainSplash|rain_splash|splash` 在 `Astra/shaders` 有 5 处命中，全部在 `lib/rain_particles.glsl`。乍看像是"已有实现"，**但读了全文之后结论相反**：

- 该文件全文只有 24 行，第 7-8 行的注释自己写明：**"Unused reference helper: no active Astra program includes or calls this filter. Particle entries retain their ordinary alpha rejection without colour-based removal."**（未使用的参考辅助函数：没有任何活跃的 Astra 程序 include 或调用这个过滤器。粒子入口保留它们普通的 alpha 剔除，没有基于颜色的移除。）
- 我实测 grep `rain_particles|astra_hide_rain_splash|astra_splash_blue` 全树 = **只有该文件自身的 3 处命中**（第 11、15、21 行，都是文件内部的定义与调用），**没有任何 include 语句**。→ 确认是死代码。
- 更关键的是**语义相反**：这个文件做的两件事是 `astra_splash_blue()`（判断一个颜色是不是原版蓝色溅落粒子：`gammaColour.b > 0.74 && all(lessThan(gammaColour.rg, vec2(0.30,0.46)))`）和 `astra_hide_rain_splash()`（如果是就**隐藏**它）。也就是"把原版溅落粒子去掉"，而 velocity 那条是"给湿地面加亮光斑"。**两者不是一回事，不构成等价实现**。

另外已核实：grep `droplet|screenRain|screen_rain|rainOnLens|enterWater|exitWater` 在 Astra = **0 命中**，所以屏幕水滴类效果也是空白（那是候选 8）。

**落地位置建议**：`program/deferred.fsh`（Astra 的延迟通道主文件，已有 `astra_volume_apply` 等合成逻辑在第 344-348 行）。需要法线与深度：Astra 在 deferred 阶段本来就有这些输入。噪声用 Astra 已有的 noisetex。

**成本**：0 新附件、0 新通道。每像素 1 次法线采样（可能已有）+ 1 次噪声采样 + 若干乘法。绝大多数像素在 `upDot > 0.6` 或距离判断处就退出了。性能影响未实机验证，但从运算量看可忽略。

**许可**：velocity-shaders 是 **MIT**（`SUMMARY-batch5.md:15` 的可代码级借用清单里已列 velocity-shaders）→ **可代码级借用**，需保留声明。

**风险提示（我的推断）**：噪声走屏幕空间 + 时间滚动，本质是逐帧变化的高频信号。Astra 对 TAA 有明确的纪律要求（`global/water/particles.glsl:20-22` 那段注释：闪烁必须是每粒子独立相位的**慢速**正弦，周期数秒，**不是帧号抖动**）。velocity 这条是快速滚动噪声，在 TAA 下可能被方差裁剪吃掉或产生蠕虫状伪影。**实施时需要在 TAA 档下实测观感**，必要时降低滚动速度或让亮斑寿命变长。

### 候选 2：天气驱动的渐变积雪

**这是什么**：雪自动积在方块的上表面，但**只在正在下雪/下雪群系里**，而且积雪有厚薄渐变（噪声决定这一小块有没有雪）、有颗粒感的法线、会改变表面反光。跟"全世界铺一层雪"的开关式做法不同，这是跟着天气走的。

**参考实现（已读源码全文，`reference_shaderpacks/arc-shader/shaders/lib/world/weather.glsl:46-105`）**：

```glsl
void ApplySnow(inout PbrMaterial material, const in float weatherNoise, const in float NoU,
               const in float viewDist, const in float blockLight, const in float skyLight) {
    float accum = saturate(2.0 * (0.96875 - skyLight));
    float snowFinal = saturate(smoothstep(-0.1, 0.4, NoU));
    snowFinal = pow(snowFinal, 0.5);
    float blockLightFalloff = saturate(4.0 * (blockLight - 0.75));
    float skySnowFinal = snowFinal * skySnowSmooth
        * smoothstep(1.0 - skySnowSmooth, 1.0, saturate(weatherNoise - accum - blockLightFalloff));
    ...
}
```

判据设计（这是本条的真正价值）：

- `accum = saturate(2.0 * (0.96875 - skyLight))`——天光越低（洞里、屋檐下），accum 越大，后面 `weatherNoise - accum` 就越难超过阈值，于是**露天才积雪**。0.96875 这个数是 247/255 附近，对应 Minecraft 天光值的编码上限。
- `snowFinal = smoothstep(-0.1, 0.4, NoU)` 再开平方——**只积在朝上的面**，且开平方让过渡更宽（稍微倾斜的面也有一点雪）。NoU 是法线与上方向的点积。
- `blockLightFalloff = saturate(4.0 * (blockLight - 0.75))`——**火把旁边不积雪**（热源融雪），方块光超过 0.75 就开始削减。
- `smoothstep(1.0 - skySnowSmooth, 1.0, ...)`——用天气强度做软阈值，雪下得越大积雪范围越广，是**连续渐变**不是开关。
- `if (totalSnow < EPSILON) return;`——不满足立刻返回，绝大多数像素在这里退出。

积雪之后的处理（第 64-104 行）也值得看：

- 雪色在 `SNOW_COLOR` 与 `POWDER_SNOW_COLOR` 之间按积雪量插值（薄雪与厚雪颜色不同）
- `material.f0 = mix(material.f0, 0.04, totalSnow)`——f0 是菲涅尔反射率基准值，0.04 是常见非金属的取值，雪盖住后表面反射特性统一成雪
- 第 82-88 行：`snowPos` 的 y 分量加 `0.12*weatherNoise` 扰动，再用 `dFdx/dFdy`（屏幕空间偏导数）叉乘求出**雪层自己的法线**，按积雪量与朝向混合进材质法线 → 雪面有起伏
- 第 91-95 行：用 `hash32(uvec2(localTex))` 生成逐纹素的随机法线，混合权重 `0.16 * totalSnow * snowDistF`，其中 `snowDistF = 1.0 - saturate(viewDist / 20.0)` → **颗粒感只在 20 格内**，远处淡出（避免远处闪烁）
- 第 97-99 行：`snowSmooth = 0.16 + 0.64 * pow4(smoothNoise)` → 光滑度也带噪声（雪面不是均匀反光）
- 第 101-102 行：`snowScatter = 0.2 + 0.2 * hash12(...)` → 雪有次表面散射
- 第 104 行：`material.albedo.a = min(material.albedo.a + totalSnow, 1.0)`

**天气驱动的接线（已核实，`arc-shader/shaders/shaders.properties`）**：

```
294: variable.float.skyWetness=if(biome_precipitation == PPT_RAIN, rainStrength, 0.0)
295: variable.float.skySnow=if(biome_precipitation == PPT_SNOW, rainStrength, 0.0)
368: variable.float.biomeSnow=if(biome_precipitation == PPT_SNOW, 0.8, 0.0)
371: uniform.float.biomeSnowSmooth=smooth(biomeSnow, 6, 6)
394: uniform.float.skySnowSmooth=smooth(skySnow, 6, 150)
```

`biome_precipitation` 是 Iris 提供的引擎变量（当前群系的降水类型），`PPT_SNOW` 是"降水形式为雪"。`smooth(x, 6, 150)` 是 Iris 的平滑插值语法（上升 6 tick、下降 150 tick），所以**雪停之后积雪会慢慢融化**（150 tick ≈ 7.5 秒），这个不对称是有意的：积得快、化得慢。

**Astra 缺口证据（实测）**：

- grep `snowAccumulation|wetnessAccumulation|SNOWY|snowAccum` 在 `Astra/shaders` = **1 命中**，且是注释：`global/lighting/wind.glsl:58` 写 "- the inSnowy leaf zeroing (wavingBlocks.glsl:58): Astra has no SNOWY_"（意思是 Astra 没有 SNOWY_WORLD，所以不需要"积雪时树叶停止摇摆"那条逻辑）
- grep `biome_precipitation|biome_temperature|biome_humidity|PPT_SNOW|PPT_RAIN|biome_wetness` 在 `Astra/shaders` = **0 命中** → Astra 完全没有使用 Iris 的生物群系天气变量。这也意味着候选 7（温湿度驱动云）共享同一个缺口。
- Astra **已有**雨天湿地面系统（README 功能边界：雨湿地面按木/土/石分材质 + 稀疏积水；实现在 `global/atmosphere/weather.glsl` 的 `astra_puddle`、`astra_wet_ground`）→ 所以"表面属性按天气覆写"这套入口 Astra 已经建好了，积雪可以复用同一个挂点，这是本条成本低的关键原因。

**与已排除项的区分（重要）**：`SUMMARY-final.md` 排除过 Complementary 的 SNOWY_WORLD（CLA 专有许可 + 全覆盖开关式）。本条**不是同一个东西**：

**落地位置**：Astra 的材质处理链，与现有湿地面同一个挂点。具体位置**未定位**，需读 `program/lit.fsh` 的材质分派段确认。注意 arc 用的是它自己的 `PbrMaterial` 结构体（含 hcm、f0、smoothness、scattering 字段），Astra 的材质表示是 4 位材质 ID 加 faceData 位域，**结构不同，不能直接搬函数签名**，要按 Astra 的表示重写。

### 候选 3：程序化熔岩（黑体辐射色 + FBM 压力场 + 高度场法线）

**这是什么**：现在的熔岩用的是原版动画贴图，所有熔岩看起来都一样，而且表面是平的。这个候选是**完全程序化地重算熔岩表面**：用多层噪声合成一个"压力场"（可以想象成岩浆内部的压强分布），压力高的地方温度高、颜色偏白亮，压力低的地方温度低、颜色偏暗红甚至发黑（冷凝的壳）；再用这个压力场推出表面的凹凸，让熔岩看起来有鼓起的岩浆团块。

**参考实现（已读全文 66 行，`reference_shaderpacks/arc-shader/shaders/lib/world/lava.glsl`）**：

```glsl
float LavaFBM(vec3 texPos) {
    float accum = 0.0;
    float weight = 1.0;
    float maxWeight = 0.0;
    for (int i = 0; i < 9; i++) {
        float p = texture(TEX_CLOUD_NOISE, texPos).g;
        accum += p * weight;
        maxWeight += weight;
        texPos *= 1.6;
        weight *= 0.6;
    }
    return accum / maxWeight;
}

#define LAVA_SPEED 24.0 // [12 24]

void ApplyLavaMaterial(inout PbrMaterial material, const in vec3 geoViewNormal,
                       const in vec3 worldPos, const in vec3 viewPos) {
    material.albedo = vec4(1.0);
    material.normal = geoViewNormal;

    float time = frameTimeCounter / 3600.0;
    vec3 texPos = worldPos.xzy * vec3(0.025, 0.025, 0.070);
    texPos += vec3(0.05, 0.05, 1.00) * fract(time * LAVA_SPEED);
    ...
}
```

各步的物理含义（这部分是本条的价值所在）：

- **FBM**（分形布朗运动，就是把同一张噪声按越来越小的尺度叠加多次，得到有层次的云状图案）：9 个倍频，每次坐标乘 1.6（尺度变细）、权重乘 0.6（贡献变小），最后除以总权重归一化。复用的是云的噪声贴图 `TEX_CLOUD_NOISE` 的 G 通道——**不需要新素材**。
- **三维噪声而非二维**：`texPos = worldPos.xzy * vec3(0.025, 0.025, 0.070)`。注意这里是 `xzy` 交换了 y/z，而且第三个分量（实际是世界的 y，即高度）用了 0.070 的更大系数，也就是**垂直方向的噪声变化比水平快约 2.8 倍**。这样竖直的熔岩墙和水平的熔岩面图案不会一样，避免"同一个图案贴在两个朝向"的廉价感。
- **流动**：`texPos += vec3(0.05, 0.05, 1.00) * fract(time * LAVA_SPEED)`。水平方向慢速漂（0.05），**垂直方向快得多（1.00）**，也就是熔岩主要沿竖直方向流动——这符合岩浆上升/下沉的直觉，比原版贴图的水平滚动更像熔岩。`time = frameTimeCounter / 3600.0` 配 `LAVA_SPEED 24.0`，所以一个循环周期是 3600/24 = 150 秒，很慢，不会让人觉得在"闪"。
- **压力 → 温度**（第 37-43 行）：
  ```glsl
  float pressure = LavaFBM(texPos);
  float coolF = 0.16 * NoU;            // 朝上面更容易冷凝（接触空气）
  float heatF = 1.0 + 0.4 * NoU;
  float heatP = 6.0 + 4.0 * NoU;       // 指数 6~10，把中间调压掉，只留极亮与极暗
  float t = min(pow(max(pressure - coolF, 0.0) * heatF, heatP), 1.0);
  float temp = 1000.0 + 15000.0 * t;   // 开尔文：1000K 暗红 → 16000K 白亮
  ```
  `NoU = abs(dot(geoViewNormal, upViewDir))` 是表面朝上的程度。朝上的面 `coolF` 大（更容易减到 0，形成冷凝壳）、`heatP` 也大（对比更强）。那个高指数 `pow(..., 6~10)` 是关键：**它把大部分区域压成接近 0（暗壳），只有压力峰值处冲到 1（白热）**，这正是真实熔岩"黑色硬壳裂缝里透出亮橙岩浆"的样子。
- **黑体辐射上色**（第 44-47 行）：
  ```glsl
  material.albedo.rgb = 0.002 + blackbody(temp) * t * 2.0;
  material.smoothness = 0.28 * pow(1.0 - t, 2.0);  // 冷凝壳更光滑（像石头）
  material.emission = saturate(3.0 * t);            // 只有热区发光
  material.f0 = 0.06 - 0.02 * t;                    // 热区反射率略低
  material.hcm = -1;
  ```
  `blackbody(temp)` 是把开尔文温度转成 RGB 的函数（黑体辐射：温度越低越红越暗，越高越白越亮）。**Astra 已经有这个函数**——`global/dimension/end_blackhole.glsl:10` 的 `astra_blackbody_rgb`（末地黑洞的吸积盘用的就是它），可以直接复用，不用重写。
  ```0.002 +``` 那个小常数是为了避免纯黑（纯黑在色调映射后可能出现色带）。
  `smoothness` 与 `emission` 都随 t 反向/正向变化，所以冷凝壳与炽热区**同时**在反光和发光两方面区分开，观感上立体得多。
- **高度场法线**（第 50-59 行）：
  ```glsl
  float heightMax = 0.8 - 0.22 * NoU;
  float height = smoothstep(0.34, heightMax, 1.0 - pressure) - pow(pressure, 0.7);
  vec3 viewPosFinal = viewPos + geoViewNormal * 0.2 * height;
  vec3 dX = dFdx(viewPosFinal);
  vec3 dY = dFdy(viewPosFinal);
  if (dX != vec3(0.0) && dY != vec3(0.0)) {
      vec3 n = cross(dX, dY);
      if (n != vec3(0.0)) material.normal = normalize(n);
  }
  ```
  这是"视差位移 + 屏幕空间求导"的经典组合：先按 height 沿法线方向把顶点位置推出去 0.2 格，再用 `dFdx/dFdy`（相邻像素的差）叉乘得到新的法线。效果是熔岩表面**真的有凹凸**，光照会在鼓起的岩浆团块上产生高光。注意它有两层防护（`dX != vec3(0.0)` 和 `n != vec3(0.0)`），因为三角形边缘或退化情况下导数可能是 0，叉乘会得到零向量，normalize 零向量是未定义行为——**这两层防护要保留，不能简化掉**。
- 第 61-63 行的 `RandomizeNormal`（用 hash 加随机法线扰动，制造颗粒感）**被作者自己注释掉了**，说明实验后效果不好。第 1-6 行的函数定义还留着但无活跃调用点。→ 不必参考这部分。

### 候选 4：末影水晶晶核发光细分

**这是什么**：末影水晶（End Crystal，末地里那个浮空的水晶，中间有个旋转的核）现在整块用同一种处理。这个候选是**把中间的晶核单独识别出来给它更强的发光**，让"外壳是玻璃、里面有个亮核"这个结构在视觉上成立。

**参考实现**：Complementary `shaders/lib/materials/materialHandling/blockEntityIPBR.glsl:6-12`，判据是 `color.g * 1.2 < color.r`（绿色通道乘 1.2 仍小于红色通道，即"偏红/偏紫而非偏绿"），命中则 `emission = 12 * color.g`。

原理是纯颜色判别：末影水晶的外壳贴图偏白/偏蓝紫，晶核贴图偏红紫，所以用"红比绿强"就能把两者分开。**这种做法的好处是完全不需要引擎提供实体部位信息**（Iris 没有"这是水晶的第几个部件"这种数据），坏处是任何偏红的方块实体都会被误判。

**Astra 缺口证据（实测）**：

- grep `end_crystal|endCrystal|crystal` 在 `Astra/shaders` = **1 命中**，是名单：`entity.properties:21` `entity.103=minecraft:end_crystal minecraft:ender_dragon minecraft:guardian minecraft:...`
- 该名单映射到 `program/lit.vsh:113` 的 `material = 10u`（对应 `entity.properties:9` 的注释 "# 103 end / anomaly mobs (eyes & body glow points)"）
- 但 `program/lit.fsh` 的 ASTRA_ENTITY 分支（第 329-332 行 `if (entityColor.a != 0.0)`）**没有任何按颜色细分晶核的逻辑** → 整个水晶（外壳 + 晶核）走同一条自发光路径

**落地位置**：`program/lit.fsh` 的 `ASTRA_ENTITY` 分支内（第 329 行附近），加一个颜色判别。Astra 的 `entity.103` 名单里除了 end_crystal 还有 ender_dragon、guardian 等，所以判别必须足够窄，或者先把 end_crystal 拆到单独的 entity ID（`entity.properties` 支持，只需新增一行）。

**成本**：0 新附件、0 新通道。每像素 1 次比较 + 1 次乘法，只在实体像素执行。极低。

**许可**：Complementary 是**专有许可**（`Astra/THIRD-PARTY.md` 与 `block.properties:70-72` 的注释都明确记录了这条纪律：只可 IDEA 借鉴，不可复制表达式）→ **仅思路级**。但这条的思路本身就一句话（"红比绿强就是晶核"），自写没有难度。

**优先级判断（推断）**：成本极低、范围极窄（只在末地、只对一种实体）。收益是末地场景的细节完整度——Astra 在末地已经做了 Kerr 黑洞 + 吸积盘 + 引力透镜这种重头戏，水晶却是默认处理，确实不协调。建议**低优先但成本极低，可以顺手做**。

### 候选 5：云的多重散射相位与 Powder 效应（银边）

**这是什么**：三个相关的现象，都是"云看起来像云"的关键：

- **前向散射银边**：站在背光位置看云，云边缘朝向太阳的那一圈会异常亮，甚至发白。这是因为光在小水滴上主要往前散射（跟雾里看到太阳周围一圈亮晕是同一个道理），薄云边缘的光几乎没被衰减就直接穿过来了。
- **多重散射**：光在云里不是只碰一次水滴就出来，而是碰很多次。只做一次散射的话云的背光面会死黑；考虑多次弹射后，暗部会有一种柔和的透亮感，云的体积感就出来了。
- **Powder 效应（啤酒定律的修正）**：只按"厚度越大越暗"算的话，云的暗部会暗得不自然（发灰而不是发黑）。真实云里光被反复吸收，暗部更黑、对比更强。这个修正在图形学里叫 powder effect（因为最早在渲染粉末/雪这类介质时用），公式很短。

**参考实现（已读源码，`reference_shaderpacks/photon-shader/shaders/include/sky/clouds/common.glsl:57-84`）**：

```glsl
float clouds_phase_single(float cos_theta) { // Single scattering phase function
    float forwards_a = klein_nishina_phase(
        cos_theta,
        2600.0
    ); // this gives a nice glow very close to the sun
    float forwards_b = henyey_greenstein_phase(cos_theta, 0.8);

    return 0.8 *
        max(forwards_a, forwards_b) // forwards lobe (max'ing them is completely
                                    // nonsensical but it looks nice)
        + 0.2 * henyey_greenstein_phase(cos_theta, -0.2); // backwards lobe
}

float clouds_phase_multi(
    float cos_theta,
    vec3 g
) { // Multiple scattering phase function
    return 0.65 * henyey_greenstein_phase(cos_theta, g.x) // forwards lobe
        + 0.10 * henyey_greenstein_phase(cos_theta, g.y) // forwards peak
        + 0.25 * henyey_greenstein_phase(cos_theta, -g.z); // backwards lobe
}

float clouds_powder_effect(float density, float cos_theta) {
    float powder = pi * density / (density + 0.15);
    powder = mix(powder, 1.0, 0.8 * sqr(cos_theta * 0.5 + 0.5));

    return powder;
}
```

逐个解释：

- **相位函数**描述"光从入射方向散射到观察方向的概率分布"。`cos_theta` 是视线方向与光方向夹角的余弦（1 = 正对太阳，-1 = 背对）。
- **Henyey-Greenstein（HG）**是最常用的近似，一个参数 g 控制前向性：g>0 前向、g<0 后向、g=0 各向同性。
- `clouds_phase_single` 用**两个前向瓣取 max**：一个是 Klein-Nishina（原本是描述 X 射线被电子散射的物理公式，这里被借来当"极窄的强前向峰"用，参数 2600 让它非常尖，作者注释说"this gives a nice glow very close to the sun"——正好产生紧贴太阳的那圈辉光），另一个是 HG(0.8)（较宽的前向瓣）。作者的注释很诚实：**"max'ing them is completely nonsensical but it looks nice"**（取最大值在物理上完全说不通，但好看）。这是图形学的常态——要记录的是"这是艺术调整不是物理"。
  再加 0.2 权重的 HG(-0.2) 后向瓣，让背对太阳时也有一点反射光（否则云的边缘在逆光下会完全消失）。
- `clouds_phase_multi` 是**三瓣混合**：0.65 前向 + 0.10 更尖的前向峰 + 0.25 后向。参数来自 `vec3 g`，在调用处是逐次迭代变化的（见下）。多重散射每弹一次，方向性就弱一点，所以后向权重（0.25）比单次散射（0.2）更高。
- `clouds_powder_effect`：`pi * density / (density + 0.15)` 是标准 powder 公式（density 很小时约等于 `pi*density/0.15` 线性增长，density 很大时趋于 `pi`，即饱和）。第二行 `mix(powder, 1.0, 0.8 * sqr(cos_theta * 0.5 + 0.5))` 是**在正对太阳时把 powder 效应关掉**（`cos_theta=1` 时权重 0.8，接近 1）——因为银边那里光几乎直接穿过，不该有"反复吸收变黑"的效果。这个耦合是设计要点，不能只抄第一行。

**多次散射的迭代实现（`include/sky/clouds/cumulus.glsl:135-188`）**：

```glsl

        scattering.x += scatter_amount *
            exp(-extinct_amount * ground_optical_depth) * isotropic_phase *
        ...
```

要点：

- **8 轮迭代**模拟多重散射。每轮衰减散射系数、放宽 powder（子代理 B 记录的循环体内做法是 `scatter *= falloff * powder`、`extinct *= 0.4`、`phase_g *= 0.8`、powder 开方放松）——我读到第 169 行为止，**循环体的完整内容未读完**，实施前需补读。
- `phase_g = pow(vec3(0.6, 0.9, 0.3), vec3(1.0 + light_optical_depth))`：注意这是 **vec3**，三个分量给三个不同的 g，也就是多重散射的三个瓣各自有不同的方向性，而且**随光学厚度变化**（云越厚，g 的指数越大，方向性越弱）。这是"厚云没有银边、薄云有银边"这个真实现象的实现方式。
- `scattering_falloff` 的 `lift(x, 0.33)` 是立方根，`mix(..., 1.0, cos_theta*0.5+0.5)` 让 falloff 在正对太阳时趋于 1（不衰减）。
- 函数返回 `vec2`：x 是散射（加光），y 是透射率（挡光）。**散射与透射分开输出**，这是 Photon 体积雾/云一贯的设计（AGENTS.md 里也提到过 Photon `water_fog_vl.glsl` 的"散射/透射分开输出"）。

```glsl
                 + cloudLightColor  * 0.9  * (0.1 + cloudShading);
```

也就是：算一个标量 `cloudShading`（来自云体光 march 的 `light`，第 490-493 行有两次密度采样：`light -= (unshiftedLight ? coarseSample : astra_2d_cloud_sample(cLightPos.xz)) * cloudShadingM;`），然后**线性地**在环境色与光照色之间插值。第 505-509 行还有一段 twilight 专属的调色板（`sunward = cube(max(0.0, 0.5 + 0.5 * VdotS))`、`horizonWarm = exp(-abs(VdotU) * 3.0)`、`litEdge = clamp(cloudShading, 0.0, 1.0)`），说明作者已经意识到需要一点视角相关性，但那是**黄昏专用的艺术调色**，不是通用散射模型。

实测 grep 结果：

- `henyey|greenstein|beer|powder` 在 `Astra/shaders` = **0 命中**（另有 6 处 powder 命中全是 powder snow 即"细雪"方块状态：`volume_fog.glsl:21`、`deferred.fsh:337`、`settings.glsl:233`、`exposure.fsh:9`、`uniforms.glsl:89` 的 `uniform int isEyeInWater; // 0/1/2/3 air|water|lava|powder snow`）
- `silverLining|silver_lining|multiScatter|multiple_scattering` = **0 命中**
- → 无散射相位函数、无多重散射、无 powder 效应，全部确认缺失

**⚠ 本节纠正我先前一个错误结论**：我在本轮早期曾断言"Photon 的多重散射全在雾文件里，云文件里没有，所以把 Photon 公式抄到 Astra 云里不成立"。**这个断言是错的**。`common.glsl` 与 `cumulus.glsl` 都在 `include/sky/clouds/` 目录下，是云的实现。错因是我按关键词命中数排序取前几个文件读，而云的命名习惯（`clouds_phase_multi`、`clouds_powder_effect`）与雾的命名（`multiple_scattering_energy`）不同，导致我漏看了 clouds 目录。详见 §6。

**落地位置建议**：改 `global/atmosphere/clouds_planar.glsl:496-502` 的光照公式。**关键优势：不需要新增 raymarch**——Astra 现有的 `light`（云体光 march 结果，第 490-493 行的两次密度采样）已经是"光穿过云走了多远"的度量，可以直接当 `light_optical_depth` 用；`cos_theta` 就是已有的 `VdotS`（第 506 行 twilight 段已经在用它）。所以落地是"把线性插值换成相位函数 + powder 调制"，不是"重建一套体积云"。

具体三步（我的推断，需实施时验证）：

1. 先只加 **powder 效应**（最便宜，5 行）：把 `cloudShading` 乘上 `pi * d / (d + 0.15)`，d 用现有的列密度。这会让云的暗部更黑、对比更强。
2. 再加 **单次散射相位**（HG 一个瓣，约 8 行）：让逆光边缘出现银边。参数从 g=0.6 起试，Photon 用 0.8。
3. 最后才考虑 **多重散射**（3 瓣 + 迭代）：这一步最贵，而且平面云没有真正的"光学厚度"概念（它是一张板），迭代版可能不适用。Photon 的解析近似（`fog/simple_fog.glsl:208-230` 的 Jessie 近似：`factor = 0.84 * albedo; energy = factor/(1-factor); scattering *= 1 + energy`）可能更适合平面云——它是纯代数不需要迭代。

**成本**：0 新附件、0 新通道。powder 约 5 次运算；HG 相位每瓣约 6 次运算（含一次除法与一次 pow）；三瓣 = 18 次。**只作用于云像素**（Astra 云有存在性测试，`clouds_planar.glsl:225` 附近），非全屏。

**耦合风险（重要）**：`docs/当前工作.md` 记录了一个未验证的问题——"天空云边缘"（编号 W07，多重轮廓，已改源码未验证）。而 `clouds_planar.glsl:346` 有一句注释提到云底会 "exposing a stack of bright contour lines"（暴露一叠亮轮廓线）。**这两个可能是同一个现象**。如果 W07 还没验证通过，不建议同时改云照明——两个改动叠在一起会分不清是哪个造成的变化，而且银边本身就会在云边缘加亮，可能放大或掩盖 W07 的症状。**建议排在 W07 验证之后**。

**许可**：Photon 是**有条件再分发**许可（AGENTS.md 与 `Astra/THIRD-PARTY.md` 记载：允许研读及一定范围再分发，但对收费和提供创作者收益的平台另有限制；且不能假定 Photon 的许可覆盖其中全部第三方片段）→ **可研读公式，系数与表达式不搬**。注意 HG 相位函数、powder 公式、Klein-Nishina 都是公开的物理/图形学结论，不属于任何包，自写实现即可。

**优先级判断（推断）**：视觉收益明显（云的质感会显著提升，尤其是日出日落的逆光场景），成本可控（可分三步走，第一步只要 5 行），但**必须排在 W07 之后**。建议**中等优先，分阶段实施**。

### 候选 6：温湿度风驱动的慢变天气系统（云型演化）

**这是什么**：现在 Astra 的云只受一个因素影响——是否在下雨（`astraRainFactor`）。这个候选是引入一套**慢变的天气状态**：温度、湿度、风速三个量各自用"世界时间驱动的 1D 噪声"缓慢随机游走，再叠加当前生物群系的影响，然后用这三个量去调制云的全部参数（覆盖率、云型、高度、厚度）。效果是云会**自己演化**——晴天的积云慢慢连成阴天，或者反过来，而不是从"晴"到"雨"瞬间切换。

**参考实现**：Photon `shaders/include/weather/core.glsl:9-116`。核心是三行慢随机：

```glsl
temperature = noise_1d(world_age) ... // 慢随机游走
humidity    = ...
wind        = ...
```

再叠加生物群系影响与 wetness，然后通过 uniform 暴露（Photon `shaders.properties:527-536`，例如 `uniform.float.biome_temperature=smooth(temperature * 2 - 1, 1000, 1000)`——`smooth(x, 1000, 1000)` 是 Iris 的平滑语法，上升下降各 1000 tick ≈ 50 秒，所以变化非常慢）。消费端在 `shaders/include/weather/clouds.glsl:118-185`，天气量驱动**全部**云参数。

**这个候选与候选 2（积雪）共享同一个缺口**：两者都需要 Iris 的生物群系天气变量，而 Astra 完全没用。已实测：grep `biome_precipitation|biome_temperature|biome_humidity|PPT_SNOW|PPT_RAIN|biome_wetness` 在 `Astra/shaders` = **0 命中**。

**Astra 缺口证据（实测 + 读源码）**：

- 云的覆盖率只受单一因子驱动：`global/atmosphere/clouds_planar.glsl:111` 的 coverage 仅用一个 `astraRainFactor`
- grep `temperature` 在 Astra = 51 命中，但**全部**是 `COLOR_TEMPERATURE` 或黑体色温（`lib/settings.glsl` 的色温滑块、`astra_blackbody_rgb` 相关），**没有任何天气温度概念**
- Astra **已有**的云基础设施（这是好消息，说明落地成本比从零低）：4 档平面云 + 时域历史（`cloud_temporal.glsl`）+ 云柱裁剪（`astra_cloud_interval`，第 218-247 行）+ 独立云影缓存（`prepare_cloud_shadow.fsh`）+ 云倒影。所以"云的参数系统"已经存在，缺的是"驱动这些参数的天气状态机"。

**落地位置建议（子代理 B 的分步建议，我认可）**：

不要一上来就建完整的温湿度系统。**第一步只做"覆盖率随湿度/温度小步演化"**：

1. 在 `shaders.properties` 加 `variable.float` 与 `uniform.float.*Smooth=smooth(...)` 声明（Astra 已有 51 处 `variable.` 与 43 处 `uniform.` 用例，语法熟练）
2. 引入 `biome_precipitation` 与一个慢变的湿度量（可以先不接温度与风）
3. 只把 `clouds_planar.glsl:111` 的 coverage 从"只看 rainFactor"改成"看 rainFactor + 慢变湿度"
4. 观察效果，再决定是否扩展到云型/高度/厚度

这样每一步都可回退，而且第一步就能看出"云会不会自己演化"的效果。

**成本**：0 新附件、0 新通道（天气量走 uniform，云参数系统已存在）。每帧几次 1D 噪声求值（在 shaders.properties 层，**每帧一次不是每像素**，成本可忽略）。主要成本是**设计与调参**——温湿度怎么映射到覆盖率、演化多快才自然，这些要试。属中高工作量。

**许可**：Photon 有条件再分发 → **可研读架构，公式与系数不搬**。`noise_1d` 与 `smooth()` 语法都是通用/Iris 内置，可自写。

**优先级判断（推断）**：视觉收益是"天空不再是静态的"，属于体验提升而非缺陷修复。成本主要在调参，代码量不大。**建议中优先，且分步做**。要注意它会让云的行为变得更难预测，与 `docs/当前工作.md` 记录的未验证问题 W07（云边缘）叠加时调试会更困难——**同样建议排在 W07 之后**。

### 候选 7：屏幕雨滴与出水镜头水流（玩法联动，全空白维度）

**这是什么**：两个相关的效果，都属于"镜头（也就是玩家的眼睛）上有水"这一类：

- **屏幕雨滴**：下雨时镜头玻璃上挂着水珠。分两种——静止的（static，附着在屏幕上不动）和下滑的（sliding，慢慢往下淌，留下痕迹）。还有"泪滴"（tearDrop）：水珠带折射和高光，像真的水滴一样把背后的景物扭一下。
- **出水镜头水流**：玩家从水里出来的瞬间，镜头上会有一道水流下来（`WATER_EXIT_STREAMS`，锯齿状的水流边缘）；入水时则有一次溅屏（`enterWater`）。

**为什么这是"全空白维度"**：这类效果把**玩家的物理状态**（在不在水里、有没有下雨、刚出水）变成**画面上的元素**。Astra 目前的玩法联动只做到了"世界表面"层面（雨湿地面、积水、涟漪），**完全没做"镜头"层面**。

**参考实现**：dercode `shaders/program/Post/Final.glsl:564-699`：

- 网格雨滴：static（固定格点）+ sliding（随时间下滑）两类
- `tearDrop`（约第 370 行）：折射 + 高光，即水滴会扭折背后的图像并在边缘加一道亮边
- `WATER_EXIT_STREAMS`：出水时的锯齿状水流
- `enterWater`：入水瞬间的溅屏
- 状态过渡用 uniform（dercode `shaders.properties:142-144`）：`exitWater` / `enterWater` 由 `isEyeInWater` 平滑得来——也就是不是"进水瞬间硬切"，而是有一个几帧的过渡

**Astra 缺口证据（实测）**：

- grep `droplet|screenRain|screen_rain|rainOnLens|enterWater|exitWater` 在 `Astra/shaders` = **0 命中**
- 相关但不同的东西 Astra 已有（避免混淆）：
  - `isEyeInWater` uniform（`lib/uniforms.glsl:89` `uniform int isEyeInWater; // 0/1/2/3 air|water|lava|powder snow`）——Astra **已经**在用它判断相机介质（水下雾、曝光、体积雾回退等都读它），所以"知道玩家在水里"这件事已经有基础，缺的是"把水画到镜头上"
  - 雨涟漪 flipbook（`global/atmosphere/weather.glsl:83+`）——那是**地面水面**的涟漪，不是镜头上的水珠
  - 水下悬浮颗粒（`global/water/particles.glsl`）——那是水里的尘，也不是镜头水珠

**⚠ 许可警告（必须先看这条）**：已实测 `_analysis/batch4_extract/dercode/` 根目录只有 `README.txt` 与 `shaders`，**没有任何 LICENSE / COPYING 文件**。按著作权默认规则，无许可声明等于**保留所有权利**（All Rights Reserved）。→ **仅思路级，且需谨慎**。不能复制任何表达式，连"照着改一改"都有风险。如果要实施，必须完全自写，只把 dercode 当作"这个效果包含哪些组成部分"的功能清单来参考。

**落地位置建议**：

- 挂在后处理链末端，`program/display.fsh` 之前或之内（这是色调映射前的最后一站）。必须在 **TAA 之后**，否则镜头上的水珠会被当成噪声抖掉；也必须在**色调映射之前**，否则水珠的高光不会参与 Bloom 与色调映射，看起来会"贴在画面上"而不是"在场景里"。这个顺序要求与 `SUMMARY-batch5.md` B06（镜头光晕）记的是同一条："应放 tonemap 前、TAA 后，否则被邻域钳制吃掉"。

**优先级判断（推断）**：这是**内容维度上的空白**（不是某个效果做得不够好，而是整类效果不存在），观感收益明显——玩家从水里出来看到镜头上流水，是很强的沉浸感反馈。但许可最脏（只能思路级）、实施细节最多（静止/下滑/折射/水流/溅屏是 5 个独立子效果）。**建议中优先，分步做**：先只做"出水时一道水流 + 入水溅屏"这两个最有反馈感的，雨滴（static/sliding/tearDrop）留到后面。

### 候选 8：发光矿石自发光（含 MIT 数据源，与 batch5 A06 同族但从未裁决）

**这是什么**：让矿石表面即使旁边没有火把，也微微发亮，方便玩家在矿洞里一眼看到矿。做法不是给矿石挂光源，而是从矿石贴图本身的颜色算出"该发多少光"——颜色越亮/越饱和的部分发光越强，石头部分不发光。这类做法在光影圈叫 **IPBR**（Internal/Implicit PBR，即"没有 PBR 资源包时，从原版贴图的颜色反推材质属性"）。

**⚠ 先说清与既有记录的关系**（这条容易误判成"已排除"，我自己也差点判错，见 §6）：

`SUMMARY-batch5.md:53` 有一条 **A06**：

> "逐像素发光筛选：block.properties 只能整方块判发光，这层再按像素通道关系判定，于同一张贴图里只有矿粒亮、石头不亮"
> 出处：realisticallyoptimized `shaders/gbuffers_terrain.fsh:17-49`（oreGlowMask 用 `1-step(0.5,abs(id-target))` 无分支比 ID，每种矿一条通道关系式）+ `block.properties:10-19`
> Astra 现状：`program/scene.glsl:393` 是整像素等比加亮 `color + albedo*((emissive+portal)*EMISSIVE_STRENGTH*0.01)`
> 许可：realisticallyoptimized MIT 可代码级（`SUMMARY-batch5.md:170` 确认）

**三条实现路线（都已读源码）**：

**路线 A：按颜色识别（Complementary 的做法）**。在 `reference_shaderpacks/complementary-reimagined/shaders/lib/materials/materialHandling/terrainIPBR.glsl`：

- 第 850 行判断钻石部分：`if (color.b / color.r > 1.5 || color.b > 0.8) { // Diamond Ore:Diamond Part`（蓝红比大于 1.5，或蓝色分量本身够高，就认定是钻石而不是石头）
- 第 857-859 行给发光：`emission = color.g + 1.5; color.rgb *= pow(color.rgb, vec3(min1(GLOWING_ORE_MULT))); emission *= GLOWING_ORE_MULT;`
- 第 862 行 else 分支走 `stone.glsl`——石头部分按普通石头处理，不发光。**这个"同一张贴图里分区处理"正是 A06 描述的能力**
- 第 866-879 行是深板岩钻石矿，用同一组判据
- 第 111 行红石用另一组：`if (color.r > 0.1 && color.g + color.b < 0.1) { // Redstone Parts`
- 第 783、789、803、809 行是金矿与深板岩金矿，判据 `color.g - color.b > 0.15 || color.r > 0.99`（第 803 行注释 `// Deepslate Gold Ore:Raw Gold Part`）

**路线 B：按方块 ID 清单（Rethinking Voxels 的做法）**。`reference_shaderpacks/rethinking-voxels/shaders/lib/materials/shadowChecks.glsl:1-60` 是一个 `bool isEmissive(int mat)` 函数，逐个列出材质 ID 并用宏分段：

```glsl
#ifdef GLOWING_ORE_IRON
        mat == 10272 || // iron ore
        mat == 10276 ||
#endif
#ifdef GLOWING_ORE_DIAMOND
        mat == 10320 || // diamond ore
        mat == 10324 ||
```

### 候选 9：附魔闪光自发光（夜里也能看见附魔光）

**这是什么**：原版给附魔物品/装备加的那层流动的紫色闪光（叫 glint），本身不发光，它是**被物品光照亮之后**才可见的。结果就是——**在黑暗的夜里，附魔闪光反而看不见**，这跟玩家的直觉相反（附魔的东西应该在暗处更显眼）。做法是把闪光贴图的亮度单独提取出来，当作自发光加性输出，这样它就不依赖环境光了。

**参考实现**：NeoLux（托管在 codeberg，作者 LucasTHCR，main 分支）的 `shaders/gbuffers_armor_glint.fsh`，全文 41 行，核心是：

```glsl
float amount = dot(col.rgb, vec3(0.3333)) * col.a;
...
gl_FragData[1] = vec4(0, 0, 0, amount);
```

也就是把闪光颜色的三通道取平均得到亮度（`vec3(0.3333)` 是等权平均，注意这跟 Astra 常用的亮度权重不同——亮度权重通常是 `vec3(0.2126, 0.7152, 0.0722)` 这类按人眼敏感度的系数，但这里只是取"有多少闪光"不需要感知正确，等权更便宜），乘上透明度，写进第二张输出的 alpha 通道，后续延迟通道再把它转成发光量。子代理已把全文存到 `shader_research/ref-sources/neolux_glint.fsh`。

该文件的注释里解释了两种直觉做法为什么都不行，这个信息很有价值：

- 直接覆盖 albedo（基础颜色）→ 物品看起来像"一块紫布"（原本的物品纹理没了）
- 直接加到 albedo 上 → 仍然被物品光照调制，夜里照样消失

所以要**单独走自发光路径**。〔读源码〕

**Astra 缺口证据（实测 + 读源码）**：

- `Astra/shaders/gbuffers_armor_glint.fsh` **全文只有 2 行**，内容是 `#include "/program/unlit.fsh"`，即直通不做任何处理（已读确认）

### 候选 10：程序化彗星（按游戏日排期的夜空事件）

### 候选 11：SDF 雨雪字形（不用原版雨贴图）

**这是什么**：原版的雨/雪是几张贴图循环平铺，玩家看久了能认出重复图案。这个候选是**完全程序化地摆放雨滴**：把屏幕按方块列划分，每列最多放 3 条"车道"（lane），每条车道上的雨滴有随机的旋转、大小、下落速度；雨滴的形状不是从贴图取色，而是从 **SDF 贴图**读取。

SDF 贴图的每个像素存的是"这个点离雨滴边缘有多远"（不是颜色），所以可以在**任意缩放下**算出平滑的覆盖率，不会像普通贴图那样放大就糊、缩小就闪。

**参考实现**：Zarya commit 68b3cb1（提交信息就叫 "glif weather"），diff 存于 `shader_research/ref-sources/diff_zarya_glif.diff`。新增文件 `shaders/common/weatherGlyphs.glsl`，包含四个函数：

- `rfScatterGlyphHit()`——车道循环加旋转（每列最多 3 条 lane，按跨度加密度）
- `rfRainSdfCover()`——核心是 `(texture(rainGlyphs, uv, -16).a - 0.5) * SPREAD` 再用 smoothstep 按像素宽度软化边缘。那个 `-16` 是纹理的**负 LOD 偏置**（LOD 是 mipmap 层级，负值表示强制读更精细的层级而不是自动选择的模糊层级）——雨丝很细，如果用自动 mip 会被模糊成一团，所以强制读最精细层
- `rfRainGlyphCover()`——5 次采样（5-tap）算覆盖率做抗锯齿
- `rfWidenWeatherSheet()`——当雨片算出来的半宽 `halfW` 小于需要的值时径向加宽。这是解决一个真实问题：**远处的雨片会细到不足一个像素，直接画就变成闪烁的线或者干脆消失**

资产是 `shaders/tex/rain_glyphs.png`。〔读源码，来自 diff〕

**Astra 缺口证据（实测 + 读源码）**：

- `Astra/shaders/gbuffers_weather.fsh` **全文只有 4 行**，是 `lit.fsh` 直通，也就是完全使用原版雨贴图（已读确认）
- grep `glyph|rain_streak|雨丝` 在 `Astra/shaders` = **0 命中**（只有 `shaders.properties` 里的 blend 混合规则命中 weather 相关配置）

## 三、引擎键情报与性能配置面候选

### 3.1 IRIS_INLINE_GLINT：26.3 分支独有，当前版本不可用

**这是什么**：Iris 在 26.3 分支新增的官方内联附魔闪光接口。有了它，着色器里写 `#if defined IRIS_INLINE_GLINT` 之后就能直接调用两个函数：`mc_hasGlint()`（这个像素有没有附魔闪光）和 `mc_sampleGlint()`（返回 glintAlpha 乘以 glint 贴图采样结果）。**不需要再单独写 gbuffers_armor_glint 程序**。

**版本门槛（已逐行比对源码确认）**：

- raw `StandardMacros.java` 的 **26.2 分支第 58-61 行没有** IRIS_INLINE_GLINT
- **26.3 分支第 61 行**有 `define(standardDefines, "IRIS_INLINE_GLINT")`
- 注入实现在 26.3 独有的文件 `pipeline/transform/transformer/GlintTransformer.java`（在 26.2 的代码树里 grep glint = 0 个文件）

**结论**：Astra 在 mc26.2 上，**没有这个宏**。Photon 在 2026-10-16（commit 9e1a441）用了这个接口——`gbuffers_all_solid.fsh:317` 写 `#if defined IRIS_INLINE_GLINT` 然后 `if (mc_hasGlint()) base_color.rgb += sqr(mc_sampleGlint())`（diff 存 `shader_research/ref-sources/diff_photon_glint.diff`）。

**这种写法在 Astra 当前版本会静默无效**——宏没定义，整个 if 块被预处理器删掉，不报错也不生效。这是一个典型的"照抄新包代码却发现没效果"的坑，而且是最难排查的那种（没有任何错误信息）。

所以候选 9 的 NeoLux 路线（自己写 gbuffers_armor_glint 程序）才是 26.2 上可行的方案。等实例升级到 mc26.3 版 Iris 之后，候选 9 可以改写成更简单的 inline 写法。

**其余 26.3 分支新键**：无。子代理逐行 diff 了 StandardMacros.java，26.3 相对 26.2 只新增了 IRIS_INLINE_GLINT 这一项。

### 3.2 Iris 没有"隔帧执行"配置键（否定结论，可省下未来的调查）

**问题背景**：Astra 的下界体素彩光是 9 个阶段的计算着色器链，同帧串行传播（README 功能边界与 `docs/当前工作.md` 的下界优化计划都提到）。一个自然的想法是"能不能让引擎每隔几帧才跑一次这条链"，从而摊薄成本。

**实测结论：不能**。我从本机 Iris 1.11.2 的解包字节码（`_analysis/irispk/`，844 个 class 文件，**无 Java 源码**）里用 Node 直接提取字符串常量，读出了 `net/irisshaders/iris/shaderpack/properties/ShaderProperties.class` 支持的**全部键前缀**：

```

texture.noise             shadow.culling           backFace.solid
backFace.cutout           backFace.cutoutMipped    backFace.translucent
rain.depth                beacon.beam.depth        frustum.culling
occlusion.culling         shadow.enabled           dhShadow.enabled
particles.before.deferred particles.ordering       scale.
size.buffer.              alphaTest.               blend.
indirect.                 program.                 bufferObject.
texture.                  customTexture.           image.

```

（另有字段 `conditionallyEnabledPrograms`、`preprocessed.properties`、`original.properties`；报错串 `Unable to parse size.buffer directive for` 与 `Custom uniforms should take the form of uniform.<type>.<name> = <expression>. Ignoring`）

**里面没有任何 interval / every-N-frames 类的键**。`ProgramDirectives.class` 的字段也只有 `drawBuffers`、`viewportScale`、`alphaTestOverride`、`blendModeOverride`、`bufferBlendInformations`、`mipmappedBuffers`、`explicitFlips`、`unknownDrawBuffers`，同样没有隔帧相关字段。它支持的注释指令是 `RENDERTARGETS`、`DRAWBUFFERS`、`LEGACY_RENDER_TARGETS`（经 CommentDirectiveParser 解析），const 指令经 ConstDirectiveParser 解析。

〔证据强度：字节码字符串提取是〔实测工具〕；"Iris 完全没有其它隔帧机制"是〔推断〕——我只查了 ShaderProperties 和 ProgramDirectives 两个类，理论上可能存在别的入口，但配置键是光影包唯一能用的接口，所以推断成立的可能性很高。〕

### 3.4 性能与配置面候选（P1-P6，子代理 C 产出 + 主代理逐条核实）

这一组的共同点：**都不加新视觉效果，而是找回被浪费的性能或修正配置正确性**。证据标记〔字节码〕= 反汇编 `_analysis/irispk/` 的 class 常量池，〔读源码〕= 直接读文件，〔推断〕= 未实测。所有性能收益**均标"未验证"**（无实机帧率依据）。

#### 候选 P1：地形 solid/cutout 入口拆分（本轮性能面最值钱的一条）

**这是什么**：GPU 有一个硬件加速叫 **early-Z**——在真正运行像素着色器之前，先用深度测试把"反正会被前面的东西挡住"的像素丢掉，省掉整段着色计算。但这个加速有个致命弱点：**只要像素着色器里出现 `discard`（丢弃像素的指令），GPU 就必须先跑完着色器才知道这个像素会不会被丢弃，于是 early-Z 被强制关闭**。

Astra 现在的问题是：**完全不透明的实体方块（石头、泥土这类）和镂空方块（树叶、玻璃这类需要 alpha 剔除的）走的是同一个程序**（`gbuffers_terrain`），而这个程序里有 `discard`（`lit.fsh:300`）。结果就是——**实体方块明明不需要任何 alpha 剔除，却因为跟镂空方块共用一个带 discard 的程序，白白丢掉了 early-Z 加速**。

Iris 1.11.2 提供了拆分的能力：引擎把实体地形和镂空地形路由到**两个独立的程序入口**，实体入口引擎自动挂 `AlphaTests.OFF`（不注入 discard），镂空入口挂 `HALF_ALPHA`。而且**如果光影包不提供这两个文件，引擎会自动回退到旧的 `gbuffers_terrain`**（`ProgramId` 的 fallback 机制）——所以这个拆分是**纯增量、零破坏**的。

**最关键的证据——Astra 已经在阴影侧用了同一个机制**：`Astra/shaders/shadow_solid.fsh` 第 2 行的注释原文：

```
// Iris 1.11.2 routes this entry only through the solid-terrain OFF-alpha key.
```

（"Iris 1.11.2 只通过实体地形的 OFF-alpha 键来路由这个入口。"）

也就是说，**Astra 的作者已经知道并在阴影投射侧用上了这个路由机制**（`shadow_solid.fsh` + `shaders.properties:358` `program.shadow_solid.enabled=SHADOWS`、`:369` `blend.shadow_solid=off`），只是**没在 gbuffer（可见表面）侧照做**。所以这条候选不是"引入一个新概念"，而是"把已有的、验证过的做法从阴影侧复制到 gbuffer 侧"——风险因此低得多。

**引擎路由链〔字节码，全部反汇编确认〕**：

- `ShaderKey` 静态初始化：`TERRAIN_SOLID` → `ProgramId.TerrainSolid` + `AlphaTests.OFF` + `Patch.VANILLA`（`_analysis/_sk_dump.txt:361-387`）；`TERRAIN_CUTOUT` → `TerrainCutout` + `HALF_ALPHA`（`:394-420`）
- Sodium 版本：`SODIUM_TERRAIN_SOLID` / `SODIUM_TERRAIN_CUTOUT` 用同样的 `ProgramId` 但 `Patch.SODIUM`（javap `ShaderKey` 输出行 1714-1769）——**Astra 跑在 Sodium 上，走的是这条**
- `ProgramId` 静态初始化：`TerrainSolid("terrain_solid", Gbuffers, fallback=Terrain)`、`TerrainCutout("terrain_cutout", Gbuffers, fallback=Terrain)`（`_analysis/_pid_dump.txt:346-391`）——`fallback=Terrain` 就是"不提供文件则回退"的依据
- `IrisPipelines` 静态表把 `RenderPipelines.SOLID_TERRAIN` / `CUTOUT_TERRAIN` / `TRANSLUCENT_TERRAIN` 映射到上述 ShaderKey（`_analysis/_ip_dump.txt:866-880`）

**Astra 缺口证据（主代理已实测复核）**：

- grep `terrain_solid|terrain_cutout|TERRAIN_SOLID|TERRAIN_CUTOUT|ASTRA_TERRAIN_SOLID` 在 `Astra/shaders` = 11 命中，但**逐条看全部是 `shadow.vsh`/`shadow.fsh` 里对 `MC_RENDER_STAGE_TERRAIN_SOLID` 这类枚举的比较**（例如 `shadow.fsh:130` `if (renderStage == MC_RENDER_STAGE_TERRAIN_SOLID && alphaTestRef <= 0.0`、`shadow.vsh:67-68`、`:143-144`、`:217`）——**这些是阴影程序里的渲染阶段判断，不是 gbuffer 程序入口**
- `Astra/shaders/` 根目录只有 `gbuffers_terrain.fsh` 与 `gbuffers_terrain.vsh`，**没有 `gbuffers_terrain_solid.*` 或 `gbuffers_terrain_cutout.*`**
- `lit.fsh` 的 discard 群（已读源码确认）：`:290` `if (albedo.a < 0.32) discard;`（雨帘，`temperature > 0.15` 分支）、`:297` `if (albedo.a < alphaTestRef) discard;`（雪保 lit 处理）、**`:299-300` `#else` 分支 `if (albedo.a < alphaTestRef) discard;`**、`:305` `if (albedo.a <= 0.0) discard;`（天气淡出）。其中 **:299-300 的 `#else` 对全部 terrain 生效，包括实体方块** → 确认实体方块现在确实走了带 discard 的路径。

**落地位置**：

1. 新增 `Astra/shaders/gbuffers_terrain_solid.vsh/fsh`（`#define ASTRA_TERRAIN_SOLID` 后 `#include` 现有的 `lit.vsh`/`lit.fsh`，就像 `shadow_solid.fsh` 那样）与 `gbuffers_terrain_cutout.vsh/fsh`
2. `program/lit.fsh` 在 `ASTRA_TERRAIN_SOLID` 下**跳过 :286-305 的 alpha/天气 discard 分支**（实体方块不需要 alpha 剔除）
3. `world1/`、`world-1/` 下已有 terrain 入口的目录同步新增
4. `shaders.properties` 把现有的 `blend.gbuffers_terrain.colortex3/16/19/20/22=off` 键**复制给两个新程序名**（blend 查找用裸 pass 名，`properties:364-367` 的注释已实测过这个规则）

**成本**：0 新附件、0 新 pass、每像素采样数不变；只多 2 个程序编译。**收益 = 实体地形碎片恢复 early-Z + 省掉 discard 分支——未验证**（需实机对比）。

**风险〔推断〕**：需实机确认 Sodium 把哪些方块送进 `SOLID_TERRAIN`（理论上应是不透明层；树叶、玻璃板等走 `CUTOUT_TERRAIN`）。**如果某个带半透明贴图的方块被错误地送进 solid 入口，它的透明部分会漏画**（因为 solid 入口跳过了 alpha 剔除）。核对方法：用 Iris 的 `patched_shaders` 调试输出或 F3 查实际路由。**这条风险是实施时的第一验证项**。

**许可**：纯引擎机制，无第三方代码。

**优先级判断（推断）**：这是本轮性能面**最值钱**的一条——机制被引擎原生支持、Astra 已在阴影侧验证过同一路由、改动是纯增量可回退、成本几乎为零。唯一不确定性是 Sodium 的方块分层是否符合预期（需实机核对）。建议**高优先，但必须先在测试环境验证方块路由再全面铺开**。

#### 候选 P2：`alphaTest.<program>=off` 去掉引擎注入的重复 discard

**这是什么**：承接 P1。Iris 会按 ShaderKey 的 AlphaTest 设置，**在变换后的着色器里自动注入一段 `discard` 代码**来复刻旧的固定管线 alpha 测试。但 Astra 在 `lit.fsh`/`unlit.fsh` 里**已经手写了 discard**——所以引擎注入的是**第二份重复的 discard**。用 `alphaTest.<pass>=off` 可以关掉引擎注入，只留 Astra 手写的那份。

**为什么值得做**：两份 discard 不只是浪费——它可能让 P1 的 early-Z 收益打折（引擎注入的那份 discard 仍在，early-Z 仍被关）。所以 **P2 与 P1 配套**：P1 把实体方块拆到无 discard 的入口，P2 确保引擎不再往里注入 discard。

**出处**：

- 〔字节码〕`ShaderProperties` 常量池 `"alphaTest."` → `alphaTestOverrides`（`handleTwoArgDirective` 族）
- 〔读源码〕photon `shaders.properties:281-299` 对 **19 个入口全设 off**；arc `:178-196` 设 **10 个**（含 deferred2/composite5/final 等全屏 pass）

**Astra 缺口（主代理已实测）**：grep `^alphaTest\.` 在 `Astra/shaders/shaders.properties` = **0 命中**。

**落地位置**：`shaders.properties` 对已有手写 discard 的入口加 `alphaTest.gbuffers_terrain=off`（P1 落地后改为 `alphaTest.gbuffers_terrain_cutout=off`；`terrain_solid` 本身引擎就是 OFF，无需键）；`unlit.fsh:32` 对应的入口（basic/textured 系）逐个核对后再加。

**成本**：每处 1 行配置。**收益 = 去掉重复 discard、部分入口恢复 early-Z——未验证**。

**风险〔推断〕**：**没有手写 discard 的入口（如 `gbuffers_weather`、`gbuffers_particles`）不能一刀切设 off**——对它们来说，引擎注入的 discard 可能是唯一的剔除手段，关掉会导致本该剔除的像素被画出来。**必须逐程序核对该程序有没有自己的 discard，再决定加不加这个键。**

**许可**：纯引擎键。

#### 候选 P3：SSR 半分辨率档（用确认空闲的 colortex7）

**这是什么**：SSR（屏幕空间反射，在屏幕上"走"一条反射光线找它撞到什么）是逐像素步进，最贵档时开销很大。**半分辨率追踪**就是只在 1/4 的像素上跑光线步进，再用深度感知上采样把结果补回全分辨率——march 的像素数直接降 4 倍。

**出处〔读源码〕**：arc `lib/common.glsl:242-248`（`SSR_SCALE` 取 1/2/4 按质量档）、`lib/ssr.glsl:13`（`viewSize/SSR_SCALE`）、`program/composite2.fsh:78`（`gl_FragCoord*SSR_SCALE` 半分辨率写入）。

**Astra 缺口（主代理已实测）**：

- `SSR_SCALE` = **0 命中**（`SCREENSPACE_REFLECTIONS` 的 12 处命中全是 lang 文本与 `shaders.properties:564` 的 `screen.WATER` 菜单项）
- Astra 的 SSR 在 `program/water.glsl:950` 起**全分辨率**走 `global/water/raytrace.glsl`（`water_raytrace`，调用点 `:781` 与 `:980`）
- **但 Astra 自己已有同款模式的先例**：`nether_reflection.fsh:38-41` 的 2×2 receiver 格点 early-return（下界岩面反射就是这么省的）——所以这套思路 Astra 作者熟悉

**落地位置（两个方案）**：

- **方案 A（省附件）**：`water.glsl` SSR 分支加 `SSR_SCALE` 编译常量 + 2×2 格点 early-return，命中辐射写入现有目标，合成侧沿用 `effect_history`/`ao_resolve` 式的深度感知上采样（Astra 已有这两个上采样实现）
- **方案 B**：`colortex7` 做专用半分辨率 SSR 目标，`size.buffer.colortex7=0.5 0.5`

**colortex7 空槽已复核**：grep `colortex7` 在 `Astra/shaders` 全树 = **0 命中**，RENDERTARGETS 注释表里也无 7 → batch5 的"唯一空槽"结论**仍然成立**。但注意 **P3 方案 B 与 batch5 C10（时序 AO）争用同一个 colortex7**，二选一或复用调度。

#### 候选 P4：`mc_chunkFade` 区块加载渐显

**这是什么**：玩家快速移动时，新加载的区块会"啪"地一下整个出现（俗称区块弹出）。这个候选让新区块**淡入**（0→1 渐显），观感更平滑。属于"加载期 LOD 平滑"，是**观感**收益不是性能收益。

Sodium 记录每个区块的加载时刻，Iris 在着色器变换时向地形程序注入一个 `mc_chunkFade` 变量（新区块从 0 渐变到 1；阴影程序里恒为 -1 表示关闭）。把雾或环境光乘上它，就能实现渐显。

**出处**：

- 〔字节码〕`SodiumTransformer` 注入 `u_Globals{...u_FadePeriodInv...}` 及 `"int chunkId = int(_draw_id);...mc_chunkFade = (chunkFade < 0) ? 1.0 : fade;"`；shadow 参数下注入 `const float mc_chunkFade = -1.0`
- 〔读源码〕complementary-reimagined `lib/atmospherics/fog/mainFog.glsl:37-38`（按距离平方混合雾）、其 `shaders.properties:116` 声明 `FADE_VARIABLE`

**Astra 缺口（主代理已实测）**：grep `chunkFade|mc_chunkFade|FADE_VARIABLE` 在 `Astra/shaders` = **0 命中**。`iris.features.optional` 现状（`shaders.properties:883`）= `CUSTOM_IMAGES COMPUTE_SHADERS`，**未声明 `FADE_VARIABLE`**。

**落地位置**：`program/lit.vsh` 或 `global/atmosphere/fog.glsl` 的雾合成处乘 `mc_chunkFade`（自写公式，如 `mix(1.0, mc_chunkFade, clamp(dist*k, 0, 1))`）；`shaders.properties:883` 的 `iris.features.optional` 行**追加** `FADE_VARIABLE`。

**⚠ 关键实现约束**：`iris.features.optional` 这个键**重复声明会互相覆盖**（不是追加），所以必须**并入第 883 行同一行**写成 `CUSTOM_IMAGES COMPUTE_SHADERS FADE_VARIABLE`，不能新开一行。`shaders.properties:880-882` 的注释已记录过这条规则。

**不确定〔推断〕**：字节码显示非 shadow 程序**无条件**注入 `mc_chunkFade` 计算，而 `FADE_VARIABLE` 标志是否真的门控这个注入**未完全确认**。落地前先用 `patched_shaders` 验证"声明 FADE_VARIABLE 前后变量是否存在"的关系——**有可能不声明也能用**（那样就省一行配置），也可能必须声明。

#### 候选 P6：云影缓存时域节流（隔帧重画）

**这是什么**：Astra 有一张云影缓存图（`colortex14`，256² 或 128²，世界锚定 2 格单元，R16 格式），存"云的影子落在地面哪里"。**它现在每帧全量重画一遍**。但云影变化很慢（云本身移动就慢），所以可以**隔帧重画**——奇数帧重画、偶数帧沿用上一帧的内容，省掉一半的 256² 重画开销。

**出处〔读源码〕**：

- complementary `program/deferred1.glsl:499`（`frameCounter % int(0.06666/frameTimeSmooth+0.5)` 帧率自适应节流先例——按帧率动态决定隔几帧，帧率高时隔更多帧）

**Astra 缺口（主代理已实测）**：`program/cloud_shadow_cache.fsh` 无任何 `frameCounter` 判断（grep = **0 命中**）。

**落地位置**：`cloud_shadow_cache.fsh` 加帧奇偶门。同缓冲隔帧复用**接受 ≤1 帧滞后**（锚点已被 CPU floor 到 2 格单元，`shaders.properties:1038-1039`，所以 1 帧滞后落在同一个 2 格单元内，视觉上无感）；或按 mellow 的奇偶双缓冲消除滞后（但**需第二个 R16 槽，与 colortex7 竞争**，见 P3）。

**成本**：0-1 附件、0 新 pass；跳过帧省整张 256² 重画——**未验证**。

**风险〔推断〕**：镜头快速移动或云快速演化时，云影可能滞后或游移，需实机调阈值。**且 `CLOUD_TEMPORAL`（Astra 云的时域历史）已有自己的时域机制，勿叠加冲突**——两套时域机制如果不同步，可能互相干扰产生 artifacts。

**许可**：机制通用；mellow MIT、complementary 仅思路参考。

**优先级判断**：收益是"晴天之外省一半云影重画"，但云影缓存本身只在 `CLOUD_SHADOWS` 开启时才有开销，且 256² 不算大。**收益中等、风险（与 CLOUD_TEMPORAL 冲突）需要小心**，建议**中低优先，且要实机验证云影滞后是否可接受**。

## 四、旧候选的新证据（不与新候选混排）

### 4.1 SH9 数组参数的 Intel 显卡兼容风险（建议优先看）

**这是什么**：Astra 用 9 个系数描述天空光的方向分布（叫球谐光照，SH9；通俗说就是用 9 个数字近似"光从各个方向照过来分别有多强"，比逐方向查表便宜得多）。Astra 的写法是把这 9 个数字作为**数组参数**传进传出函数。Photon 的作者发现 Intel 显卡驱动处理不了这种写法，于是改掉了。

**证据**：Photon commit a715d94（2026-10-16）的注释原文：

> "Intel just can't handle arrays (as parameters or returned values) properly"
> （Intel 就是没法正确处理数组——无论作参数还是作返回值）

该 commit 把 `float[4]` 改成 `vec4`、`float[9]` 改成 `mat3`（3×3 矩阵正好装 9 个数），并删除了整个 `spherical_harmonics_fallback.glsl`。子代理已存 diff 到 `shader_research/ref-sources/diff_photon_sh.diff`。〔读源码 + 在线核实〕

**Astra 的对应位置**：

- `Astra/shaders/lib/sky_sh9.glsl:69`：`astra_sh9_basis(vec3, out float basis[9])`
- `Astra/shaders/lib/sky_sh9.glsl:111`：`astra_sh9_accumulate(inout vec3 coefficients[9], ...)`

两处正是"数组作参数"的形态（`out float basis[9]` 是输出数组，`inout vec3 coefficients[9]` 是读写数组）。

**必须说清楚的证据强度**（按 AGENTS.md 要求把实测与推断分开）：

- 这**不是** Astra 的功能缺口。Astra 的 SH9 早就存在并且工作正常。
- 这**也不是**已确认的 bug。我没有 Intel 核显实机，无法验证 Astra 在 Intel 上是否真的出问题。
- 这是一条**风险注记**：如果将来有用户在 Intel 核显上报告天空光相关的编译失败或渲染异常，这里是第一嫌疑点。
- 改法本身是低风险的（`float[9]` → `mat3` 是纯数据类型重排，数学内容不变，9 个数还是那 9 个数），但**是否现在就改，属于用户决策**——按 AGENTS.md，参考项目的做法不自动成为 Astra 的缺陷或实施要求。
- 一个反对现在改的理由：`mat3` 是列主序的 3×3 矩阵，用它装 9 个 SH 系数会**丢失语义**（读代码的人看不出这是球谐系数而不是变换矩阵），可读性下降。Photon 之所以能接受，是因为它同时删掉了 fallback 文件、整体重构了那部分。Astra 如果只是为兼容性而改，可能得不偿失。

**另一条相关但不适用的情报**：Photon 同一个 commit 还用了 subgroup（子组，一种让同一批 GPU 线程互相交换数据的特性，比走共享内存快）来加速 SH 计算。这条**对 Astra 不适用**，因为 Astra 的 SH 是在片元着色器里算的（`program/sky_irradiance.fsh`，输出到 colortex18 的 9×1 纹理），而 subgroup 加速只对计算着色器（compute shader）里的 SH 生成器有意义。已实测 grep `subgroup` 在 Astra = **0 命中**，Astra 没有用这个特性。

### 4.2 Zarya 的 LPV 传播化简，反向印证 Astra 的做法是对的

**背景**：LPV 是 Light Propagation Volume（光传播体），通俗说就是把空间切成小格子，让光从一个格子"扩散"到相邻格子，从而算出彩色间接光。Astra 的下界体素彩光就是这个思路（`program/nether_light.csh`，9 阶段同帧传播）。

**新证据**：Zarya 在 commit 0377170 里把自己的 6 邻居传播**从能量加权均值退化成纯 max**——原来是 `mix(mean, energy, 0.6)`，改成 `max(n0..n5)`；衰减系数从 0.70-0.88 改成 0.58-0.92（diff 存 `shader_research/ref-sources/diff_zarya_mixcol.diff`）。

**Astra 现状（已核实）**：`Astra/shaders/program/nether_light.csh:118-122` 已经是 max 传播：`incoming = max(incoming, neighbour); color = max(color, incoming * 0.72)`。

**结论**：Astra 的做法与 Zarya 演化的终点一致，**无需改动**。

这条的价值是"减少一次自我怀疑"——如果将来有人提议把 max 改成加权均值以求"更物理"，可以指出**两个独立项目都从加权均值退回到了 max**。加权均值听起来更物理（能量守恒），但实际会让光在传播中糊成一团、失去边界；max 会丢失能量守恒但保留了光的锐利边界，视觉上更好。这是"更物理 ≠ 更好看"的一个实例。

## 六、本轮纠正的错误判断（按 AGENTS.md 要求记录，避免后续沿用）

AGENTS.md 明确写了："宁可说不知道，不要给一个听起来合理但没核实的答案"，并要求把实测与推断分开。本轮**我自己犯了三个错误、子代理犯了两个**，全部记录如下。这些错误本身是有价值的信息——它们指出了调研方法上的陷阱。

### 6.1 主代理（我）的三处错误

**错误 1：断言"Photon 的多重散射全在雾文件里，云文件里没有"**

- 当时的原话大意：Photon 的 `multiple_scattering` 都在 `fog/simple_fog.glsl`、`fog/water_fog_vl.glsl`、`fog/end_fog_vl.glsl`，云文件里没有，所以"把 Photon 公式抄到 Astra 云里"不成立。
- **实际情况**：Photon `include/sky/clouds/common.glsl:57-84` 有完整的 `clouds_phase_single` / `clouds_phase_multi` / `clouds_powder_effect`，`cumulus.glsl:135-188` 有 8 轮迭代的多重散射。云的多重散射**存在**，而且比雾里的更完整（三瓣相位 + powder + 逐迭代变化的 g）。
- **错因**：我先用 grep 统计各文件的命中数，然后**只读了命中最多的 fog 目录**，没有按目录枚举去检查 clouds 目录。Photon 在云里用的是 `clouds_phase_multi` / `clouds_powder_effect` 这种命名，在雾里用的是 `multiple_scattering_energy`——**同一个概念，两套命名**。
- **教训**：关键词命中数不等于机制存在与否，命名习惯不同的实现会整片漏掉。**应当按目录枚举候选文件，而不是按关键词命中数排序取前几名**。这个教训与 `SUMMARY-batch5.md` ⑨ 反面缺陷库第 8 条"死代码骗选项扫描"是同一类问题的两面：那边是"命中了但没实现"，这边是"实现了但没命中"。

**错误 2：断言"本地包无熔岩表面流动增强实现"**

- **实际情况**：arc-shader 有完整的 `shaders/lib/world/lava.glsl`（66 行，FBM 压力场 + 黑体色 + 高度场法线），而且是 MIT 许可。
- **错因**：我 grep 的模式是 `lavaAnimat|LAVA_VISION|lavaVision|flowingLava|lavaFlow`——**全是我猜的宏名**。而 arc 的函数叫 `ApplyLavaMaterial` / `LavaFBM`，文件名是 `lava.glsl`。我的模式一个都没匹配上。
- **教训**：查"某个东西有没有实现"时，**应该先按文件名 glob**（`**/lava*`、`**/*cloud*`），再读文件；猜宏名是最不可靠的方式。本轮我后来正是靠 `glob("**/lava*")` 一步找到了。

**错误 3：断言"雨滴溅落不是缺口，Astra 已有 `global/atmosphere/rain_particles.glsl`"**

这条错了**两次**：

- **路径错**：实际文件是 `Astra/shaders/lib/rain_particles.glsl`，不在 `global/atmosphere/`。（我一度用 `fs.readFileSync` 读错误路径得到 ENOENT，才发现。）
- **结论错**：更重要的是我没读全文就下了结论。读了之后发现两件事：
  1. 该文件是**死代码**——全文 24 行，第 7-8 行自己写明 "Unused reference helper: no active Astra program includes or calls this filter. Particle entries retain their ordinary alpha rejection without colour-based removal."；我实测 grep `rain_particles|astra_hide_rain_splash|astra_splash_blue` 全树只有该文件自身的 3 处命中（第 11、15、21 行），**没有任何 include 语句**。
  2. 语义**相反**——它做的是 `astra_splash_blue()`（判断颜色是不是原版蓝色溅落粒子）与 `astra_hide_rain_splash()`（如果是就**隐藏**它），而 velocity 的 HELIOS_RAIN_SPLASH 是给湿地面**加亮光斑**。一个做减法一个做加法。
- **教训**：**文件存在 ≠ 机制存在 ≠ 被调用**。这正是我在 §6.1 错误 1 里总结的同一条纪律的另一面。而且讽刺的是，`SUMMARY-batch5.md` ⑨ 反面缺陷库第 8 条已经写过"死代码骗选项扫描"——我在给别人写基线的时候自己踩了同一个坑。以后写"Astra 已有 X"之前，必须确认 X 的调用链是活的。

### 6.2 子代理的两处错误

**错误 4（子代理 B）：判断"Astra 缺半分辨率体积雾缓冲 + 上采样，这是 VOLUMETRIC_FOG 默认开的最直接降本路径"**

- **推翻依据（全部实测）**：
  - Astra **已有**三档体积雾分辨率：`shaders.properties:170-177` 在 `#if defined VOLUMETRIC_FOG && VOLUME_FOG_DENSITY > 0` 下按 `VOLUME_FOG_QUALITY` 分档，`:171 #if VOLUME_FOG_QUALITY == 0` → `:172 size.buffer.colortex23=0.25 0.25`；`:174` 是 `0.5 0.5`；`:177` 是 `1 1`。
  - 默认档就是最低档：`lib/settings.glsl:237` `#define VOLUME_FOG_QUALITY 0 // [0 1 2]`，也就是 **0.25 × 0.25 = 1/16 的像素量**，比 Photon 的默认 `VL_RENDER_SCALE = 0.50`（1/4 像素量）**更低**。
  - `shaders.properties:582` `profile.QUALITY=profile.BALANCED ... VOLUME_FOG_QUALITY=1` 说明高档位只在 QUALITY 预设开启。
  - 上采样**已经是边缘感知的**：`global/atmosphere/volume_fog.glsl:233-282` `astra_volume_resolve`，注释原文（第 233-238 行）"Edge-aware upsample of the reduced-resolution S/T buffer to a full-resolution pixel. A tap is dropped when its own geometry (depthtex0 at the tap centre) does not belong to this pixel's surface, so silhouettes do not inherit a march that ended on background terrain; sky taps carry no medium and never dilute geometry. If no tap survives, the pixel falls back to the analytic prefix march."。实现含四重保护：`:262` 天空剔除（`tapDepth >= 0.999999 || referenceZ <= 0.0`）、`:268-270` 深度带权（`band = 1.0 - smoothstep(0.02, 0.06, abs(tapZ - referenceZ) / max(referenceZ, 1e-3))`）、`:274-275` 材质标志剔除（`flags & 128u`）、`:280` 失败回退解析式（`astra_volume_prefix_medium`）。
- **结论**：子代理提的"降本路径"Astra 已经走完了，而且走得比 Photon 更远（默认分辨率更低、上采样保护更多）。**这条候选不成立**。
- **剩下唯一可能的新意**是空间滤波（luster `c1_blend_layers.fsh:229-243` 的 `fog_spatial_filter`，实现在 `include/fog/smoothing.glsl:11`）。已实测 Astra grep `spatial_filter|denoise|blur` 在 `global/atmosphere` = 1 命中且无关（`fog.glsl:181` `fogFactor *= smoothstep(0.01, 0.015, fogFactor)`）。但**在默认 0.25 档下再加空间滤波能否改善观感、还是会让雾更糊，未验证**；而且 Astra 的边缘感知上采样本身就有平滑效果，两者可能重复。→ 只能作为"如果将来把默认档提到 0.5 想省回来"的备选，不是当前候选。
- **教训**：子代理报"缺 X"时，主代理必须自己 grep 一遍 Astra。子代理读的是参考包，容易先入为主地认为"参考包有的 Astra 就没有"。

**错误 5（子代理 B）：把发光矿石判为"已排除"**

- 子代理给的理由是"batch5 同类 + 方块光颜色表排除"。
- **核实结果**：`SUMMARY-batch5.md:53` 确实有同族的 **A06**（逐像素发光筛选，realisticallyoptimized MIT），但 A06 **只是被记录在候选表里，从未被裁决**——grep `发光矿石|glowing.?ore|GLOWING_ORE` 在 `docs/` = **0 命中**，也就是 `docs/参考与取舍.md` 的"不重新尝试的旧方案"里没有它。而 `shader_research/complementary-reimagined.md:89` 与 `:138` 两处明确把它列为**待做候选**并评估"提升高（矿洞场景观感直接受益）、工作量低"。
- **结论**：判断过严。"batch5 记录过"≠"batch5 排除了"。已作为候选 8 写入。
- **教训**：排除清单有三层，必须分清——(a) `docs/参考与取舍.md` 的"不重新尝试的旧方案"是真裁决；(b) `SUMMARY-*.md` 的候选表只是**记录**，不是裁决；(c) 各包调研笔记（`complementary-reimagined.md` 等）是原始素材。只有 (a) 能用来判"已排除"。

| P5 | `dhShadow.enabled=false`+`dhClouds=off` | 引擎键 | 极低（2 行配置） | **正确性**（DH 用户兜底） | 无（不装 DH 的用户零影响） | **高**（顺手做） |
| P2 | `alphaTest.<pass>=off` | 引擎键 | 极低（每处 1 行） | 性能（去重复 discard） | 与 P1 配套；逐程序核对是否已有手写 discard | **中高** |
| P4 | `mc_chunkFade` 区块渐显 | 引擎注入变量 | 极低（0附件0pass，1 uniform） | 观感（区块加载不闪） | 须并入 `iris.features.optional` 同一行；先用 patched_shaders 验证 FADE_VARIABLE 是否门控注入 | **中** |
| P3 | SSR 半分辨率档 | arc MIT（建议自写） | 低（方案A 0附件 / 方案B 占 colortex7） | 性能（SSR 像素 -75%） | 方案 B 与 batch5 C10 争 colortex7 唯一空槽 | **中** |
| P6 | 云影缓存隔帧重画 | 机制通用（mellow MIT） | 低（0-1附件0pass） | 性能（省一半 256² 重画） | **勿与 CLOUD_TEMPORAL 时域机制叠加冲突**；需实机验证滞后 | **中低** |

### 7.2 三条建议（我的判断，非实测）

**建议一：先做候选 1、8、9 这三条。**

理由：三条都满足"0 新附件、0 新通道、许可干净、改动局部"。而且它们填的是同一类空白——**玩法联动视觉**（雨、矿、附魔都是"游戏里发生了什么"在画面上的反映），Astra 目前在这一维度上只做了地面湿润与水下颗粒。三条加起来的工作量大约是"改三个文件 + 加一段 block.properties"，而观感变化是玩家一眼能看到的。

**建议二：候选 5 与 6（云相关）必须等 W07 验证完再动。**

`docs/当前工作.md` 记录的 W07（天空云边缘多重轮廓）已改源码但**未验证**，而 `clouds_planar.glsl:346` 的注释提到云底会 "exposing a stack of bright contour lines"——这两者很可能是同一个现象。银边效果本身就是在云边缘加亮，**如果 W07 还没定论，加银边会让症状更难判断**（是 W07 没修好，还是银边参数不对？）。这是可预见的调试泥潭，避开它的成本只是排个顺序。

**建议三：候选 7（屏幕雨滴）先做两个子效果就够。**

dercode 无 LICENSE 是硬约束（只能思路级），而它包含 5 个子效果（static 雨滴、sliding 雨滴、tearDrop 折射、WATER_EXIT_STREAMS、enterWater 溅屏）。**"出水时一道水流 + 入水溅屏"这两个反馈感最强**（玩家一定会经历入水出水，而且那一刻的视觉反馈最直接），雨滴那三个可以先不做——下雨时镜头挂水珠在 MC 玩家的习惯认知里并不是必需项，而且它与候选 11（SDF 雨丝）功能重叠。



**建议四：性能组先做 P1+P5+P2 这三条，且 P1 必须先实机验证方块路由。**

P5（`dhShadow`/`dhClouds`）只有 2 行配置、对不装 DH 的用户零影响，是纯保险，**随时可做**。P1（地形入口拆分）是本轮性能面最值钱的一条，但它有一个**必须先在测试环境验证的前提**：确认 Sodium 到底把哪些方块送进 `SOLID_TERRAIN`。如果某个带半透明贴图的方块被错误送进 solid 入口，而 solid 入口跳过了 alpha 剔除，它的透明部分会漏画成不透明。**验证方法**：用 Iris 的 `patched_shaders` 调试输出看实际路由，或在测试世界放一批各类方块逐个看。验证通过后，P2（`alphaTest.=off`）作为配套跟上——但 P2 要**逐程序核对**，没有手写 discard 的入口（weather/particles 等）不能设 off，否则该剔除的像素会漏画。

**P3/P4/P6 都建议等实机数据再决定**：P3（SSR 半分辨率）收益要看 SSR 在当前帧时间里的占比；P4（`mc_chunkFade`）是观感不是性能，且 `FADE_VARIABLE` 是否门控注入还没确认；P6（云影节流）与 `CLOUD_TEMPORAL` 的时域机制有潜在冲突。这三条都不该在没实测的情况下先动。
### 7.3 明确不建议做的（本轮新增判断）

- **体积雾降本**：Astra 已经做到 0.25 档 + 边缘感知上采样，比参考包更远（见 §6.2 错误 4）。
- **下界体素链隔帧降频**：引擎无此键，自己做等于引入历史缓冲，与"同帧无历史"的既有裁决冲突（见 §3.2）。
- **froxel 体积雾**：本地无任何参考实现，等于从零设计一套新架构，而 Astra 已有 raymarch 体积雾且已默认降采样——收益不明。
- **信标光束着色**：参考包的做法只是硬编码颜色滑块，属风格向（见 §5.1）。
- **气泡柱**：本地主流包都没有着色实现（见 §5.2）。
- **SH9 改 mat3**：不是缺陷，只是风险注记；改了会损失可读性（见 §4.1）。
- **阴影贴图隔帧渲染**：引擎侧无任何阴影更新频率/间隔帧键（`shadowIntervalSize` 是**空间**吸附不是时间节流，Astra 已用于 `lib/settings.glsl:453-457`，主世界设 0.0 并注释了理由）；本地 7 包也**均无**实现——mellow 的 `frameCounter%2` 是体素双缓冲，complementary 的取模节流是末地 vlFactor 状态机，都不是阴影贴图。**此路不通**（见 §3.2）。
- **天空 SH 计算化**：Photon 有 `d4a_generate_sky_sh.csh` 并行归约，但 Astra 的 `sky_irradiance.fsh` 是 9×1 像素 quad × 64 采样，绘制成本本身可忽略，compute 化**零收益**（子代理 C 裁决）。

## 十、给下一轮接手人的话

如果你要继续这项工作，建议的顺序是：

1. **先读 §6**（本轮纠正的错误）。那里记的三个陷阱——"命名不同导致漏查"、"猜宏名不可靠"、"文件存在≠被调用"——在做任何新的缺口判断时都会再遇到。
2. **候选 1、8、9 可以直接开工**，前置条件都写在表里了。三条都是 0 附件 0 通道的局部改动。
3. **候选 5、6 等 W07**。先确认 `docs/当前工作.md` 里 W07 的验证状态。
4. **候选 3 先解决噪声源问题**（未确认项 #3），那是它唯一的技术前置。
5. **§3.3 那 4 个引擎键**（`rain.depth`、`beacon.beam.depth`、`particles.before.deferred`、`backFace.*`）适合单独开一个小任务逐个核实，不要和视觉候选混在一起做——它们是正确性问题不是功能问题，判断标准也不同。
6. **§2 的 26.3 适配**等实例升级后再做，但清单已经具体到资源 ID 了，到时候是纯执行。升级时记得回归测试所有读深度的逻辑（Iris 1.11.4 的 depth transformer 变更）。

最后一句提醒：本报告里所有"成本"估计都是**从源码读出来的运算量推断**，没有一条经过实机帧率验证。Astra 的性能目标是原生 1080p 平均 ≥144 FPS，任何候选实施前后都应该实测对比，不能引用本报告的成本描述作为性能结论。
