## 2026-09-12 第十六轮（末地传送崩溃：诊断与修复）

用户传送末地时**进程直接死亡**。实例日志最后一行是

是**原生层崩溃**，从开始创建末地管线到进程死亡约 **34 秒**。这是 **GPU 挂起**的典型特征。

**根因（量化）**：`end_blackhole.glsl` 的测地线步进循环里，**每一步调用两次
`end_scene_segment`**（段起点 + 段中点），每次都要遍历候选天体、逐个做包围球测试，
命中后还要跑 96 步的表面搜索。
- 256 步 × 2 次 = **512 次场景求交 / 像素**

## 2026-09-17 SC-39：修正上一轮（2026-09-16）的三处实现错误 + 据调研做性能优化

上一轮的三项修改被外部审核指出"实现与注释相反"。逐条数值复核后**三条全部属实**，其中一条比审核描述的更严重。

### 1) 高亮压缩实际压暗中间色、并放大强高亮（最严重）
上一轮把 `astra_twilight_highlights` 换成逐通道 shoulder 再按亮度重标定：
`return color * luma(color) / luma(max(shoulder, color))`。
数值实测（`qa` 临时脚本，未入库）：
- 中间色被压暗：`(0.6,0.5,0.35)` → ×0.601、`(1.0,0.15,0.1)` → ×0.376、`(0.1,0.25,1.0)` → ×0.321，连**纯灰 0.5 也被压成 ×0.588**。只有"三通道绝对值相同"的对角灰不受影响，所以肉眼看不出来——它无声地把画面里所有饱和中间色乘了 0.3~0.6。
- `peak=true` 分支是**反压缩**：`shoulder - knee + color` 在高于 knee 时会超过输入。日盘 `(8,7,5.2)` 输出 `(6.68,5.85,4.34)`，比色调映射上限高 6.7 倍，而这个分支的名义职责正是"给日盘一个上限"。

修正：退回**峰值相对的统一缩放**（全局单一系数，通道比例严格不变，且单调不增），去掉逐通道形式与 peak 分支。
实测：低于 knee 恒等不变（中间色与饱和色全部原样通过）；高于 knee 时色相比例误差 0；与上一轮之前**实际出厂**的 twilight 公式逐点比对偏差 **0.000000**；灰色与饱和色斜坡 0→10 全程**零放大**。日盘峰值 8.0→2.35，方盘仍高于色调映射 knee（保持"亮"）但不再 6.7 倍超限。

### 2) 植被透光方向写反（该效果从未生效）
`diffuse.glsl` 里 `viewDir = normalize(-playerPos)` 是**表面指向相机**；`worldLightVector` 是**表面指向光源**（sunPosition/100 经 sunPathRotation 与视图→世界转置，其世界 Y 在正午为正——同文件 `worldSunVector.y` 即太阳高度角，`sky.fsh` 也用 `-worldSunVector` 放月亮，均为此佐证）。两者点积正午约 **-0.8**，于是 `if (vdotl <= 0.0) return 0.0;` 把整个效果判死。参考式是 `dot(nViewPos, lightVec)`，其 `nViewPos` **由相机指向场景**，即 Astra 的 `-viewDir`。修正为 `dot(-viewDir, worldLightVector)`。

### 3) 水坑反射用的是广域潮湿遮罩，不是稀疏水坑遮罩
上一轮把 `surfaceWet`（广域潮湿）写进 colortex3.a，并在 deferred 里由它反推"积水权重" `smoothstep(0.30,0.85,wet)`。广域潮湿在雨天几乎处处饱和到 1，因此该权重≈1——**昂贵的 96 步积水反射仍然跑遍全湿世界**，正是同一轮声称要消除的"泛白的反射块"；而真正为该用途算出来的 `astra_puddle()` 稀疏遮罩**被写到哪儿都没有**。

修正：稀疏遮罩改走 `colortex0.a`（R11F_G11F_B10F 的未用 A 通道；该 pass 的 deferred 变体只读 colortex0.rgb，composite1 的 bloom 捕获与 final 也只读 .rgb，故无消费者受影响；TRANSLUCENT 变体排除，它们有真实混合 alpha）。涟漪法线振幅同时改为按积水宽度缩放，于是"有没有涟漪"本身成为 deferred 可直读的"这里有没有水"的第二重确认。反射门控现为 `积水遮罩 × 朝上度 × 涟漪存在 × 菲涅尔`。这也是本轮最大的**性能回收**：96 步射线步进回到它本来该覆盖的稀疏水坑上。

修正水坑遮罩时我把它写进 `colortex0.a`，并在注释里断言"R11F_G11F_B10F 的 A 通道是未用填充，因此该值能原样读写"。**该断言是编造的**：权威声明 `lib/water_buffer_formats.glsl:12` 明确写 `colortex0Format = R11F_G11F_B10F`，这是 **RGB 格式，没有 alpha 通道**。写入被丢弃、读取返回 1.0，于是 deferred 里 `standingWater > 0.15` 会**在每一个像素上成立**——反射重新跑遍全世界，与 GPT 指出的原错误症状完全相同，只是换了个成因，而且这次还附了一条声称安全的注释。

### 2) 我的 `power()` 是**负优化**，且我上一轮刚给它的"正确性"背书
`power(exponent, base)` 用循环做平方链，但调用点传的是运行时指数（`isLeaves ? 10.0 : 6.0`）。指数不是编译期常量时循环无法折叠，于是额外背上 `mod`/`floor` 的指数记账与循环携带依赖——**比它替换掉的 `pow()` 更慢**。已删除该通用形式，并把规则写进文件头：**字面整数指数才走助手，其它一律 `pow()`**。相应地：`pow5(square(v))` 与 `pow6(v)` 各自字面化、云的两个 `pow(v,3.0)` 改 `cube()`、天空调色板的 2.9 与 0.90 曲线**退回 `pow()`**（非整指数无链可折叠，近似会改画面）。

### 3) 末地光照改动既不是中性、也没达成目的（第二次尝试才对）
修正#1 里我把 `0.25 * sqrt(...) * 1.22` 换成 `0.65 * sqrt(...)` 并断言"两端点相等"。算术没错、结论错：**0.62 不是旧权重的最大值（1.0 才是）**，所以最亮面从 0.305 掉到 0.65 的量级换算后整体**暗了约 12%**，而我又一次在注释里写了"亮度不变"。第二次改成只夹上界 + 保留原系数，结果**又没达成目的**——只夹上界意味着最暗面亮度和以前一模一样，可读性收益为**零**（实测 1.00x）。第三版才用显式下界 `clamp(visibility*ndotl, 0.15, 0.62)`：实测最亮面 1.00x（与出厂逐值相同）、背光面 1.38x、明暗比 2.66x→1.58x（保住了以黑洞为方向依据的阴影关系）。

### 4) 四处共同点，以及这一轮真正该记住的
**注释描述意图、代码做别的事，而我用"注释读起来对"代替了"数值算过"。** 这与上一轮 GPT 抓到的三处是同一失效模式，说明我上一轮补的两道校验（数学助手逐点比对、压缩类函数全量程验证单调性）**只覆盖了"新写的数学"，没覆盖"我对已有代码行为的断言"**。本轮已把断言也纳入复核：`colortex` 格式与 blend 状态、每个写入通道的读写者、每个 pass 的 RENDERTARGETS、以及每个"亮度不变/端点相等"声明的数值验证。四处里只有第 2 处（pow 助手本身）是被上一轮已有的校验覆盖到的，其余三处都是"对系统行为的错误断言"，需要的是**查声明与消费者，而不是再算一遍公式**。
